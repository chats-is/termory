## Current App

Tauri v2 desktop app for browsing local history records from supported AI tool clients, plus their on-disk memory and skill files.

Supported sources in the current code:

- Codex
- Claude Code
- Gemini CLI
- OpenCode
- Grok Build (xAI — sessions + memory (`<grok-home>/memory/`) + skills + provider switching + session/project delete + official-quota (weekly/monthly credit window); no migrate)

Top-level UI shell — six activity-rail routes (⌘1..6 in order):

1. **Providers** — third-party API platform switcher (per CLI). Default landing route. One tab per managed app: Claude Code / Codex / Gemini / OpenCode / Grok Build (the five CLIs) **plus Claude Desktop** — the GUI app, managed via its 3P gateway profile (direct mode only); its tab always shows (like the other apps), and install/platform gates activation + the InstallGuide + gateway binding, NOT tab visibility. See "Claude Desktop (3P gateway profile)" under Providers.
2. **Records** — chat / transcript history. Three internal panes:
   - *Sessions* — per-tool transcripts
   - *Memories* — on-disk memory files (CLAUDE.md, AGENTS.md, GEMINI.md, `~/.codex/memories/`, `~/.claude/projects/<slug>/memory/`, etc.)
   - *Skills* — `SKILL.md` files under each tool's skills directory plus the cross-tool `.agents/skills/` location
3. **Favorites** — saved per-message snapshots
4. **Search** — substring search + Cmd-K palette
5. **Stats** — KPI cards + all-history calendar heatmap + a Tokens chart (Type / Model breakdown)
6. **Settings** — Appearance / Storage / Search history / Keyboard shortcuts / About

Plus a **system-level macOS menu-bar tray** (outside the in-app rail) for quick provider switching — see "Menu-bar tray" below.

Current alignment target: data acquisition and message preview formatting should follow the official tools. UI layout, source filters, project grouping, search, stats, cross-source sorting, and the Memory/Skills views are app behavior and do not need official UI parity.

- JSON parsing: `serde`, `serde_json`

- Time handling: `chrono`

Current Tauri IPC commands (64 registered in `generate_handler!`), called from the frontend with `invoke(...)`:

**Scan & detail**
- `scan_all_sessions` — returns `ScanResult { projects: Project[], records: AppSession[] }` (see "First-class projects" — `projects` are enumerated folders/entities; `records` are session/memory/skill entries distinguished by `source`)
- `load_session` — loads one entry by `{ source, id }` (the path is resolved backend-side via `SESSION_PATH_INDEX`, never passed by the frontend)
- `search_all_sessions(query)` — case-insensitive substring search across all loaded session/memory/skill bodies (minimum query length: ONE character — a single CJK char is a valid query, user decision 2026-07-17; hits aggregate one per record); each `SearchHit` carries `first_match_index` for scroll-to-message

**CLI detection**
- `detect_clis()` — runs `which`-style probes for `claude` / `codex` / `gemini` / `opencode` binaries; returns `{ [app]: boolean }` for the Providers page InstallGuide gate. **Codex counts as installed when EITHER the CLI binary OR the desktop app is present** (they share `~/.codex/` auth + config, so provider management works with just the app). The desktop app is detected by macOS bundle id `com.openai.codex` scanned under `/Applications` + `~/Applications` (`codex_app_info_in`) — NEVER by `.app` name: since the 2026-07-09 merge the Codex app IS the unified ChatGPT desktop app (existing installs updated in place, so it's named `ChatGPT.app`; ChatGPT Classic keeps `com.openai.chat`). Windows distribution of the app is **Microsoft-Store-only** (no direct `.exe`/`.msi` on openai.com/download per OpenAI's own docs), so an MSIX package is the only install form to check (unlike macOS's `/Applications` scan). **Windows detection is split by cost, because `probe_codex_installs` feeds `detect_install_snapshot`'s HOT PATH (every tray-menu open / watcher rescan, on the caller/main-event thread) and a `Get-AppxPackage` spawn there loads the Appx module (0.5–1.5s cold) — it would freeze the tray on every click, whereas macOS's equivalent is a cheap plist read**: (1) **presence** (`providers::codex_appx_installed_in`, the hot-path `app: bool`) is a pure filesystem `read_dir` of `%LOCALAPPDATA%\Packages\` matching a `OpenAI.Codex_<publisherhash>` dir (the PackageFamilyName — publisher-hash suffix varies per signing identity, so prefix-match `OpenAI.Codex_`, never a hardcoded hash; this per-user Packages dir is readable, unlike `WindowsApps\`) — the SAME mechanism as Claude Desktop's `msix_package_roaming_parents`, path-injected + compiled off-Windows so it's unit-tested on any host; (2) the app **version** (`providers::codex_appx_version`, PowerShell `Get-AppxPackage -Name 'OpenAI.Codex' | … PackageFullName`, silent via `output_with_timeout`, parsed from the `PackageFullName`'s second `_`-segment by `parse_appx_package_version`) is fetched ONLY on the cold path via `providers::probe_codex_installs_detailed` (the `detect_codex_installs` IPC — Providers page load + Recheck; `app_version` is `None` in the hot-path `probe_codex_installs` and is discarded by `detect_install_snapshot` anyway, so nothing hot pays for it). Detect by package NAME (`OpenAI.Codex`), never the DisplayName — Windows brands the taskbar/Start entry "ChatGPT" (shared with the unified app) but the package identity stays `OpenAI.Codex` (confirmed on a real installed package name, `OpenAI.Codex_26.707.9564.0_x64__2p2nqsd0c76g0`, openai/codex#32772). **No Windows `bundledCli`**: MSIX packages install into the ACL-restricted `C:\Program Files\WindowsApps\`, which a normal process can't `read_dir`/open into, so there's no Windows equivalent of `<bundle>/Contents/Resources/codex` — `codex_binary()` stays standalone-CLI-only on Windows. Like Claude Desktop's Windows paths, the PowerShell version fetch + real package layout are unverified on real hardware (the filesystem presence scan + version parse ARE unit-tested off-Windows).
- `detect_codex_installs()` — Codex's install forms split: `{ cli, app, appVersion, bundledCli }`, probed backend-side by `providers::probe_codex_installs_detailed` (the cold-path variant: on macOS a single bundle resolution (`codex_app_info_in`) feeds `app`/`appVersion`/`bundledCli` from one Info.plist read; on Windows the cheap `probe_codex_installs` presence scan plus a PowerShell version fetch — see the `detect_clis` bullet for the hot/cold split). `bundledCli` is the runnable codex CLI shipped INSIDE the desktop app (`<bundle>/Contents/Resources/codex`, a self-contained native binary on the app's release channel — alpha builds) — the **fallback for app-only installs**: `providers::codex_binary()` = standalone CLI first, else bundled, and every codex spawn/launch seam routes through it (the `codex login` spawn in accounts.rs; terminal resume / New Session via `codex_shell_invocation()` in terminal.rs, which uses bare `codex` when the standalone CLI exists and the bundled binary's single-quoted absolute path otherwise — the bundled branch is macOS-gated, no Windows quoting path exists). Account add / re-login disable only when BOTH `cli` and `bundledCli` are false (`codexCliMissing` in ProvidersPage / `reloginUnavailable` on OfficialAccountsSection) — in practice that state means "no codex at all" (the tab shows InstallGuide), so the disabled-button tooltip is defensive. The frontend "Copy resume command" intentionally keeps the canonical bare `codex resume <id>` (it documents the command, not the fallback path). **Tray plumbing (`providers::InstallSnapshot`)**: `detect_install_snapshot()` returns `{ map: HashMap<CliApp,bool>, codex_terminal }` in one probe pass — `codex_terminal` = standalone CLI (INCLUDING the interactive-shell fallback, since the user's terminal resolves what the fixed-dir scan may miss) OR bundled CLI. The tray stores/compares the WHOLE snapshot (`INSTALLED` cache + `menu_installed_stale`), so a codex-terminal flip (standalone CLI added/removed while the app stays) triggers a full rebuild, and `terminal_clis` reads `snapshot.codex_terminal` with ZERO filesystem work on the main thread (the probe always runs on the caller's thread: watcher / IPC worker / tray-click handler).
- `detect_cli_versions_cmd()` — invokes each detected CLI with `--version` so the Providers page can show actual installed versions. The Codex entry is the CLI version ONLY; the frontend composes the Official card's version line from both forms via `codexVersionText` (provider-utils) → `v0.142.5 (CLI) · v26.707.31428 (App)` (whichever installed; labels are deliberate keep-English i18n keys `providers.codexVersion{Cli,App}`). `ProviderOfficialCard.version` is now preformatted text rendered verbatim (callers add the `v` prefix).

**Records migration & deletion (see "First-class projects, migration & deletion")** — frontend sends `(project, rel)`, never a raw path
- `migrate_claude_project(old_path, new_path, delete_old)` — move a renamed project's whole slug dir (sessions + companion `<id>/` dirs + auto-memory) into the new path's slug dir; returns `ClaudeMigrationResult { sessions, memory_files, old_dir, new_dir, new_project }`
- `migrate_claude_session(project, rel, new_path, delete_old)` / `migrate_claude_memory(project, rel, new_path, delete_old)` — migrate one session (+ companion dir) / one auto-memory; located by `project + rel`
- `migrate_codex_session(id, new_path)` / `migrate_codex_project(project, new_path)` — re-point a Codex session / a whole cwd's sessions to `new_path` by rewriting the rollout `payload.cwd` (authoritative — the `threads` table is a backfill cache) + `UPDATE threads.cwd`; returns `CodexMigrationResult { sessions, new_project }`. Pure metadata rewrite (no file move — Codex rollout files stay in `~/.codex/sessions/`). Project form includes archived. See "Migrate (Claude + Codex + Gemini)".
- `migrate_gemini_project(project, new_path)` — re-point a Gemini project's history to `new_path` by rewriting its `.project_root` ownership markers (tmp + history base dirs); gemini self-heals its `projects.json` registry from the markers on next run, so no file move + no registry write. Project-level only (Gemini sessions are project-scoped). Returns `GeminiMigrationResult { sessions, new_project }`. See "Migrate (Claude + Codex + Gemini + OpenCode)".
- `migrate_opencode_session(id, new_path)` / `migrate_opencode_project(project, new_path)` — re-point an OpenCode session / a whole cwd's sessions to `new_path` via `UPDATE session SET directory = ?, path = NULL` (by id / by directory); `project_id` left intact (no empty-project resurrection, no registry write). Returns `OpencodeMigrationResult { sessions, new_project }`. Regrouping convenience (resume-by-id works across renames). See "Migrate (…)".
- `migrate_grok_session(id, new_path)` / `migrate_grok_project(project, new_path)` — MOVE a Grok session / a whole cwd's session dirs into the destination cwd's `encode_cwd_dirname`-derived dir (`fs::rename`) + rewrite each `summary.json` info.cwd. Grok resumes per-cwd by scanning the encoded dir, so files physically move (paths change → `old_dir`/`new_dir` in the result for the frontend remap). Returns `GrokMigrationResult { sessions, new_project, old_dir, new_dir }`. See "Migrate (…)".
- `delete_claude_project(project)` — `remove_dir_all(~/.claude/projects/<sanitize(project)>)` (never touches the cwd)
- `delete_claude_session(project, rel)` / `delete_claude_memory(project, rel)` — delete one record, path built from `project + rel` + `is_safe_rel`
- `delete_gemini_project(project)` / `delete_gemini_session(project, rel)` / `delete_gemini_memory(project, rel)` — same, under `~/.gemini/tmp/<id>/` matched by `.project_root`.
- `delete_codex_session(id)` / `delete_codex_project(project)` — **real delete of sqlite rows by id/cwd + the rollout files**. Codex's `threads` table is a CACHE rebuilt from rollout files (see codex_follow.rs), so deleting only the row is reverted by backfill — we `fs::remove_file` each `rollout_path` FIRST, then `DELETE FROM threads WHERE id|cwd = ?`. **File-first is deliberate:** a crash after the committed DELETE but before file removal would let backfill resurrect the row; removing the authoritative file first means a crash leaves only a harmless re-deletable orphan row, never a resurrection. Project delete removes ALL of a cwd's threads INCLUDING archived ones (user-confirmed "delete = full"). `delete_codex_memory(rel)` removes one `.md` under `~/.codex/memories/` (bounded by `is_safe_rel`; Termory never reads `memories_1.sqlite`, so nothing to sync).
- `delete_opencode_session(id)` / `delete_opencode_project(project)` — `DELETE FROM session WHERE id` / `DELETE FROM project WHERE worktree` with `PRAGMA foreign_keys = ON` so the `ON DELETE CASCADE` to message/part (and project→session) fires; the session table is a durable primary store (NOT a replayed projection — verified OpenCode never replays events on startup), so a direct DELETE is permanent. Session delete also removes the session's **sub-agent children recursively** (`opencode_session_tree` walks the `parent_id` tree — `parent_id` has NO FK cascade, so we mirror the official `session.remove()` which recurses into `children()`). ALSO clears the `event`/`event_sequence` log for every removed aggregate (`clean_opencode_events`, skipped on older DBs without those tables) — mirrors `sync.remove()`. OpenCode has **no deletable memory** (its memory is the user's own AGENTS.md/CLAUDE.md project + global instruction files, never touched). All Codex/OpenCode DB writes open RW with a 1.5s `busy_timeout` and surface "database is locked — quit the running {app}" (`map_db_locked`) when the app holds the lock. For Codex this means either the CLI or the Codex app (they share auth and state). Frontend sends `{ id }` / `{ project }` / `{ rel }` (NOT `(project, rel)` — these are DB rows, not files); wired in `ListItemMenu.tsx` (session + Codex memory) and the sidebar project row in `App.tsx`. **Local list update keys by `sessionKey` (`source:path:id`), NOT `path`:** DB-backed sources (OpenCode) share ONE db-file path across all sessions, so a path-keyed `removeRecordsLocally`/tombstone (`App.tsx`) wrongly cleared the whole list and the deleted rows reappeared on rescan — the id in `sessionKey` disambiguates. Tests: `sessions::tests::delete_codex_*` / `delete_opencode_*`.
- `delete_grok_session(id)` / `delete_grok_project(project)` — Grok is FILE-based (dir-per-session). `delete_grok_session` resolves the session's `<grok-home>/sessions/<encoded-cwd>/<uuid>/` dir via the scan path index (the scanned log file — `chat_history.jsonl` or `updates.jsonl` — → parent), bounded to the grok sessions root, and `remove_dir_all`s it — the SAME local removal as the official `JsonlStorageAdapter::delete_session` (jsonl/mod.rs:1197, NotFound-tolerant). It then mirrors the official delete's second step (`delete_session_history` → `notify_session_updated` → `delete_doc`, persistence.rs:2458 / search_fts.rs:286): `evict_grok_search_docs` runs `DELETE FROM session_docs WHERE session_id = ?` against the ONE GLOBAL `<sessions-root>/session_search.sqlite` (FTS5 follows via the schema's AFTER DELETE trigger — "callers only touch session_docs"). Eviction is BEST-EFFORT (locked/missing DB → log-only): the index is a self-healing derived cache (per-session refresh drops missing docs; `reindex_all` prunes orphans). The official delete's THIRD step — removing the cloud writeback copy via `BackendClient::delete_session_data` — is deliberately NOT done: Termory manages local data only, and deleting a local record ≠ intent to destroy the cloud copy (a synced session may still show as `remote` in grok's own list). `delete_grok_project` removes every `<encoded-cwd>` dir whose sessions record that cwd (`info.cwd`, authoritative — the encoded dir name is never decoded) and evicts each removed uuid's search doc (dir names ARE session ids; the index lives at the sessions ROOT, so it does NOT die with the cwd dir); the cwd's OWN skills under `<cwd>/.grok/skills` are NOT touched (grok delete only removes session history). `migrate_grok_session(id, new_path)` / `migrate_grok_project(project, new_path)` MOVE the `<id>/` session dir(s) into the destination cwd's `encode_cwd_dirname`-derived dir (`fs::rename`) + rewrite each `summary.json` info.cwd — grok resumes per-cwd by scanning that encoded dir, so the files must physically move; returns `GrokMigrationResult { sessions, new_project, old_dir, new_dir }` (see "Migrate (…+ Grok)"). `delete_grok_memory(rel)` removes one `.md` under `<grok-home>/memory/` ($GROK_HOME-aware, bounded by `is_safe_rel`) — Grok's cross-session memory is human-readable Markdown on disk (xai-grok-memory `storage.rs:58` = `grok_home().join("memory")`; global `.md` at the root, workspace-scoped under `{project-slug}-{blake3_hash8}/` subdirs, `storage.rs:24-31`), so it mirrors `delete_codex_memory` (a plain `fs::remove_file`). **There IS a per-workspace `index.sqlite`** (RAG chunks + FTS, `storage.rs:110`) but Termory deliberately does NOT evict from it — unlike the grok SESSION delete (which clears `session_search.sqlite`), grok's memory index has a **first-party self-heal**: `xai-grok-memory/watcher.rs:3-9` runs a live fs watcher on `<grok-home>/memory/` that calls `MemoryIndex::delete_path` on a `.md` REMOVE event, and `grok memory reindex`/`doctor` prune orphaned chunks (`index.rs:1182`, official regression test). So a Termory-side delete is reconciled by grok itself on next run; replicating the more complex memory-index schema here would be higher-risk for no durability gain (session-search has no such watcher, which is why THAT one is evicted). `$GROK_HOME` is a real official override (`xai-grok-config/paths.rs:35` — env var first, else `~/.grok`), so the frontend detection is $GROK_HOME-robust by design (below). Frontend: `ListItemMenu.tsx` (session, `delete_grok_session`; auto-memory `isGrokAutoMemory` — unlike the marker-based Claude/Gemini/Codex memory branches this is **$GROK_HOME-robust**: a grok memory record's `project` IS the `<grok-home>/memory` root (the scan passes it verbatim), so the rel is `relUnderRoot(project, path)` regardless of where grok-home lives, and the `"grok"` tool tag — passed as `memoryTags` ONLY from the Memories pane, and grok never tags a project-instruction file — identifies it without a hardcoded `.grok` path → `delete_grok_memory`) + the sidebar project row in `App.tsx` (`delete_grok_project` + `migrate_grok_project`). Tests: `sessions::tests::grok_delete_session_and_project_scoped`, `delete_grok_memory_in_removes_md_and_guards_path`, frontend `ListItemMenu.test.tsx` (default + custom-$GROK_HOME rel) + `session-utils.test.ts` (`relUnderRoot`).

## Release & Updater

CI: `.github/workflows/test.yml` runs on every push/PR (docs-only changes — `**.md`, `docs/**` — are paths-ignore'd) — vitest + `npm run build` (type-check) on ubuntu, and `cargo test --lib` on an ubuntu + macos + **windows** matrix (the release workflow only builds; the Windows leg is what actually executes the `#[cfg(windows)]`-gated tests, e.g. `windows_open_command`/`executable_candidates`). `tauri::generate_context!` needs `../dist` to exist at compile time, so the rust job stubs `dist/index.html` first.

GitHub Actions workflow at `.github/workflows/release.yml` is triggered when a `v*` tag is pushed (e.g. `git tag v0.2.0 && git push --tags`) or manually via `workflow_dispatch`. It uses `tauri-apps/tauri-action@v0` and builds installers for:

- macOS Apple Silicon (`aarch64-apple-darwin`)
- macOS Intel (`x86_64-apple-darwin`)
- Linux x86_64 (`x86_64-unknown-linux-gnu`) — with apt deps for webkit2gtk-4.1, soup-3.0, javascriptcoregtk-4.1, etc.
- Windows x86_64 (`x86_64-pc-windows-msvc`)

A draft GitHub Release is created with the platform installers attached plus `latest.json` (the updater manifest). Review & publish the draft.

### One-time signing key setup (DONE as of v0.2.6)

The updater only installs artifacts whose signature matches a pubkey baked into the binary. Without a keypair, in-app updates won't work (but the GitHub Actions builds still produce installers — users can download manually).

**Status: configured.** The keypair lives at `~/.tauri/termory.key` (local, password-protected — back it up; losing it means no more signed updates for existing users, and the locked bundle id makes that unrecoverable). The pubkey is baked into `tauri.conf.json` `plugins.updater.pubkey`, `bundle.createUpdaterArtifacts` is `true`, and the GitHub repo secrets `TAURI_SIGNING_PRIVATE_KEY` + `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` are set. Signed updater artifacts (`.sig` + `latest.json`) ship from v0.2.6 on, so **auto-update works only for users already on ≥0.2.6** — earlier installs (no baked pubkey) must download the new version manually once. CI still creates a **draft** release; publish it (un-draft) so `…/releases/latest/download/latest.json` resolves.

The original setup steps, kept for reference / re-keying:

```sh
# Generates ~/.tauri/termory.key (private, password-protected) + termory.key.pub
npx @tauri-apps/cli signer generate -w ~/.tauri/termory.key
```

Then:

1. Paste the contents of `~/.tauri/termory.key.pub` into `tauri.conf.json` `plugins.updater.pubkey`.
2. Add GitHub repo secrets:
   - `TAURI_SIGNING_PRIVATE_KEY` = contents of `~/.tauri/termory.key` (the private file)
   - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` = the password you set during generation
3. Tag and push: `git tag v0.2.0 && git push --tags` — the workflow builds, signs, and publishes a draft release.

Bump `src-tauri/tauri.conf.json` `version` and `src-tauri/Cargo.toml` `version` together before tagging so the binary self-reports the right version.

macOS bundle identifier: `is.chats.termory` (reverse DNS of the `chats.is` domain the project ships under). Do NOT change this after a public release — macOS treats a different identifier as a different app, so existing user data and the Tauri updater would break.

### Why ancestor walk gates on `.git`

All three open-source tools refuse to ascend without a project-root marker:

- **Codex** (`codex-rs/core/src/agents_md.rs`): `DEFAULT_PROJECT_ROOT_MARKERS = &[".git"]`. The doc-comment on the loader: *"If no marker is found, only the current working directory is considered."*
- **Gemini** (`packages/core/src/utils/memoryDiscovery.ts findProjectRoot`): defaults to `['.git']`. When no marker is found, returns null → caller sets `ceiling = startDir` → `findUpwardGeminiFiles` breaks immediately on the start dir.
- **OpenCode** (`packages/opencode/src/project/project.ts`): `worktree` is resolved via `git rev-parse --git-common-dir`; without git the fallback sets `worktree: sandbox` (= cwd), so `Filesystem.findUp(start=cwd, stop=cwd)` collects only cwd.

Claude Code (the only one NOT gating on `.git` — its `attachments.ts` walks to fs root) is the outlier; for simplicity we apply the stricter (more common) rule. This is a known minor mismatch documented in [`codex-ancestor-walk-rule`](memory).

The implementation lives in `scan_memory`:

1. `push_project_root_instruction_files(cwd, ...)` always runs (cwd-level files including `.claude/CLAUDE.md`).
2. `find_git_root(cwd, home)` walks up looking for `.git`. Returns `Some(dir)` or `None`.
3. If `Some(git_root)` and `git_root != cwd`, walk from `cwd.parent()` up to and including `git_root`, calling `push_ancestor_instruction_files` at each level (omits `.claude/CLAUDE.md`).
4. The final dedup-by-path keeps each file's first label; ancestor files get their own ancestor dir as the project label.

### Unified tool-message format — LOCKED RULE

Every tool message — regardless of source platform — uses the same markdown shape. This is a hard rule: any new tool / structured-result formatter MUST follow it without exception.

**Shape:**

`````
{status} **{Verb}**({args})

⎿ {summary}              ← present when the tool has a structured summary
                           (line counts, status codes, settings, etc.)

```{lang}                ← optional fence for diff / source / structured output
{body}
```

or

````                     ← 4-backtick fence for unstructured text output
{body}                     (avoids collision with content containing ```)
````
`````

**Rules:**

1. `{status}` glyph: `⏺` success, `✗` failure (Claude `constants/figures.ts:4` + Codex `exec_cell/render.rs:236`). Cross-platform — applied to every tool card.
2. `{Verb}` text is platform-native (Claude `userFacingName`, OpenCode `routes/session/index.tsx`, Codex `exec_cell/render.rs`, Gemini `displayName`); the wrapper shape `**Verb**(args)` is identical across platforms.
3. `{args}` always passes through `wrap_inline_code` (sessions.rs:48) so embedded backticks / `*` / `()` don't break markdown.
4. **`⎿ ` prefix is REQUIRED on every summary line**, with one trailing space before the content. Tools without a structured summary skip the line entirely (Bash, generic MCP, etc.). NEVER put `⎿` inside a code fence — browser monospace fonts render U+23BF inconsistently, breaking column alignment.
5. Summary content matches the per-tool Claude TUI component verbatim (count bolding, label pluralization). Examples:
   - `⎿ Read **N** lines` — `FileReadTool/UI.tsx:138-139`
   - `⎿ Wrote **N** lines to **{file}**` — `FileWriteTool/UI.tsx:58`
   - `⎿ Found **N** {label}` — `GrepTool/UI.tsx:32-33`
   - `⎿ Added **N** lines, removed **M** lines` — `FileEditToolUpdatedMessage.tsx:42-50`
   - `⎿ Received **{size}** ({code} {codeText})` — `WebFetchTool/UI.tsx:31-58`
   - `⎿ Error: Exit code N` (Codex) / `⎿ Error: {message}` (Claude — no exit code)
6. Reasoning across all platforms: `format_reasoning_body(content)` → `> *line*` italic blockquote.
7. **No content is dropped to match official TUI behavior.** Suppressed tools (Claude `TodoWrite`, `AskUserQuestion`, `EnterPlanMode`, etc.) and synthetic / contextual wrappers (Codex `<environment_context>`, OpenCode `synthetic` parts, Claude `<tick>` / `<local-command-caveat>` / NULL_RENDERING attachments) all surface in Termory — usually as italic `*[wrapper-name]*` notices when there's no structured representation. Termory is a history browser; hiding things misleads the user.

### Helpers used across all four platforms

- `wrap_inline_code(content)` (sessions.rs:48) — CommonMark §6.1: pick a backtick delimiter longer than the longest run inside the content; pad with spaces when content starts or ends with a backtick. Used everywhere an unsafe user payload (path, command, URL, query, pattern) becomes inline `\`code\`` in markdown.
- `format_reasoning_body(content)` (sessions.rs:71) — line-by-line `> *...*` italic blockquote, escapes stray `*` / `_` so italic spans can't break mid-line.
- `merge_tool_outputs(messages)` (sessions.rs runs in `parse_claude_session` and `parse_codex_session`): folds matching `tool_result` / `tool_error` into the leading `tool_use` card. On a matched failure it prefixes the leading line with `✗ ` (instead of `⏺ `) and prepends the fence body with `Error:` (plus `Exit code N` when `SessionMessage.exit_code` is set). Orphan results (no matching tool_use) keep their text but also get a `⏺` / `✗` status prefix.
- `codex_parse_exec_output(text)` returns `CodexExecOutput { raw, exit_code }` — strips Codex's `Chunk ID: ... Output:` wrapper line-by-line so the visible body is just `aggregated_output`, AND extracts the exit code for the `Error: Exit code N` line.
- `codex_parse_patch_actions(patch_text)` scans `*** Add/Delete/Update File:` markers and returns `Vec<CodexPatchAction>` for the apply_patch header builder.
- `strip_ansi(text)` — drop ANSI escapes (CSI colour / cursor codes, OSC title-set sequences, and lone `ESC + letter` escapes). Used for OpenCode Bash output (`routes/session/index.tsx` l.2041) and `type: "shell"` message captures (`context/data.tsx` l.192). No regex crate — small inline state machine, leaves non-ESC content untouched.

### Markdown rendering (frontend)

## History and Preview Behavior

- Session lists should come from the same stored records the official tool uses for its history/resume list.
- Session list fields should use official values when available: title, project/cwd, timestamps, source id, and original path.
- Loading a session should parse the underlying transcript/messages for that exact selected record.
- Message previews in the detail pane should show the same user-visible content style as the official tool, including command/tool output formatting.
- **Show everything that was recorded.** Termory deliberately surfaces content that the official TUIs hide (Claude's suppressed tools, `<tick>` / `<local-command-caveat>` / NULL_RENDERING attachments / `isMeta` user messages; Codex's `<environment_context>` / `<user_instructions>` / `<skill_instructions>` / etc.; OpenCode's `synthetic` parts). The transcript is the source of truth — hiding things makes the history misleading. List-time filters (`isSidechain`, `kind === "subagent"`) that decide *which sessions* appear in the list are separate and still apply.
- Compatibility readers are allowed only for real older/alternate storage layouts and should not override the current official path.

## Implementation Rules

- Keep data acquisition and message preview formatting aligned with the official tool behavior, but **never hide content** — Termory is a history browser, so anything recorded must be surfaced (usually as an italic `*[wrapper-name]*` notice when there's no nicer representation). See the "Unified tool-message format — LOCKED RULE" rule 7.
- Do not add custom title/message fallbacks unless the official tool does the same.
- Format command and tool output the way the official tool **actually renders it in its TUI** — not what its docs say, and not what feels right. Always grep `.audit-sources/<repo>/` for the real render function and put a `// path/to/file.tsx:LINE` citation next to the matching Termory branch. Earlier rounds of this codebase had ~600 lines of tool-formatting guesswork that diverged from every TUI; those have been replaced and the rule exists to prevent regressing.
- Treat UI behavior separately from official data behavior. Source filters, project grouping, search, stats, cross-source sorting, and the Memory/Skills views are app UI behavior.
- Keep changes scoped. Avoid unrelated refactors.
- **Cross-platform is a hard requirement (macOS / Linux / Windows).** The release CI builds all four targets (macOS arm64 + x64, Linux, Windows) on every `v*` tag — keep it green, and don't let a single-platform API leak into a shared path. Concretely:
  - Gate every OS-specific call behind `#[cfg(...)]`: `cfg(unix)` for `chmod`/permissions (with a `cfg(not(unix))` fallback), `cfg(target_os = "macos")` for Dock / `set_dock_visibility` / tray niceties, per-OS branches for CLI-binary PATH probing and the filesystem watcher.
  - `src-tauri/src/main.rs` carries `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]` — without it the Windows release binary uses the console subsystem and a terminal window opens alongside the app on launch. DO NOT REMOVE (debug keeps the console so logs stay visible).
  - **Every SILENT subprocess spawn must go through `providers::hide_console`** (std `Command`; for tokio use `creation_flags(providers::CREATE_NO_WINDOW)`): on Windows a GUI-subsystem parent flashes a console WINDOW for every console child, and `.cmd` shims (all npm-installed CLIs) are additionally routed through `cmd.exe` by the Rust runtime — so even `codex --version` pops a cmd window without the flag. Applied at `output_with_timeout` (version probes), terminal.rs `where_` detect, the OUTER `cmd /C start` helper (the inner `start` still opens the real terminal window), and the `codex login` capture. NEVER apply it to a terminal-launch spawn the user is meant to see (wt / powershell branches). Same mechanism as cc-switch (`misc.rs` `CREATE_NO_WINDOW` on every silent spawn); its extra explicit `cmd /D /S /C call` + `raw_arg` form for `.cmd` shims was deliberately NOT adopted — Rust ≥1.77's implicit `.cmd` routing covers our only-arg-is-`--version` case, and hand-rolled `raw_arg` quoting reopens the escaping risk the runtime hardening exists for.
  - Resolve each CLI's data path to what THAT tool actually uses per-OS. Claude/Codex/Gemini use home-relative dotdirs (`~/.codex`, …) on all platforms. OpenCode uses xdg-basedir → `~/.config` / `~/.local/share` on **every** OS including Windows, so build those via `home().join(".config/…")` and **do NOT use `dirs::config_dir()` / `dirs::data_dir()`** for them (those return `~/Library/Application Support` on macOS and `%APPDATA%` on Windows — both wrong for these tools). Cite the upstream path source.
  - Build paths with `PathBuf::join` from `home()` / `dirs::*` — never string-concatenate with `/`, and no shell/`.exe` assumptions outside a `cfg`. **Never call `dirs::home_dir()` directly — use `crate::home_dir()`** (lib.rs): in TEST builds it honors the `HOME` env override on every OS (plain `dirs::home_dir()` on Windows resolves via SHGetKnownFolderPath and ignores the environment, which made every HOME-override test silently read/write the runner's real profile); release behavior is identical to `dirs::home_dir()`.
  - Backend tests use a `HOME` override (`testutils::override_home`, honored by `crate::home_dir()`'s test-build env seam) and run on ubuntu + macos + **windows** in CI (test.yml). **Known Windows test note:** the original `migrate_claude_*` tests and the absolute-path `decode_claude_project_slug` assert are `#[cfg(unix)]`-gated — their fixtures are unix-path-shaped (Windows `fs::canonicalize` adds the `\\?\` prefix and JSON escapes the backslashes, so the substring asserts can't hold verbatim). All three migrate flows now ALSO have `#[cfg(windows)]` counterparts — `migrate_claude_session_in_rewrites_windows_cwd`, `migrate_claude_project_move_mode_rewrites_windows_cwd`, `migrate_claude_memory_in_windows_preserves_subpath_and_rejects_stray` — each using a `C:\…` cwd, deriving the expected `new_canon` the same way production does (canonicalize → strip `\\?\`), and PARSING the migrated JSONL to assert the decoded `cwd` (dodging the backslash-escaping that blocked the substring asserts). Their logic is platform-agnostic, so each was verified locally by temporarily switching its gate to `#[cfg(unix)]` before restoring `#[cfg(windows)]`; on Windows CI they run for real. Green tests ≠ full runtime verification; call out anything that needs real-device testing.
- Add or update tests when changing a parser or formatter. Skill/memory scanners have parallel tests at the bottom of `sessions.rs` — extend that block when adding scan paths. Tool-rendering tests should assert verbatim strings (e.g. `"**Search**(pattern: \"TODO\", path: \"src\")"`), not regex matches, so renames are caught.
- When adding a new scan location for an existing tool, verify against the tool's official source first (then docs as a secondary reference); do not infer from naming conventions alone.

## Providers (switch CLI to a third-party API platform)

User flow: a Provider is a named snapshot of `{baseUrl, apiKey, model, ...}`. Each CLI has its own list. Activate = materialize into the CLI's live config so the next launch picks it up. Switching back to Official = clear the Termory-injected fields; the CLI's native OAuth/credentials file is **never touched**, so logins survive a round-trip.

**Local storage** — `~/.termory/` (same path on macOS / Linux / Windows), permissions `0700` dir / `0600` files on Unix. Atomic write (tmp + rename):

- `~/.termory/config.json` — UI prefs (`records_pane`, `providers_app`, `recent_searches`). No secrets.
- `~/.termory/providers.json` — provider library. On disk it's `{ "version": N, "providers": [...] }` (`PROVIDERS_SCHEMA_VERSION = 1` in `config.rs`) where `providers` is a UNIFIED array holding BOTH per-CLI providers (`kind: "official"|"custom"`) and gateways (`kind: "gateway"`). `config.rs` splits/merges by `kind`: `read_providers()` returns `kind != "gateway"`, `read_gateways()` returns `kind == "gateway"`, and each writer preserves the other kind (`entry_is_gateway`), so the strongly-typed `Vec<Provider>` parse (tray, IPC) never sees a gateway entry. `read_all_entries` runs the array through `migrate_entries(version, entries)` (a no-op at v1 — the seam where a future schema bump hooks its upgrade). No bare-array / old-`gateways[]` compatibility (clean dev baseline). Contains API keys, `0600`. **Lenient config parsing (LOCKED — valid JSON must never error):** config content that is syntactically valid JSON must NEVER make the code error, even when it holds a value THIS build doesn't recognize. The canonical case is a **downgrade**: an older binary reads a providers.json a newer version wrote, containing e.g. a `grok` provider/binding for an app this build has no feature for. That is Termory's OWN legitimate data from another version (NOT arbitrary foreign junk), so the unrecognized entry is **skipped** (simply absent from this version's UI — "unknown" ≠ "error") and everything else keeps working; only a real JSON *syntax* error may fail. Mechanism (all in providers.rs): `providers_from_json` / `gateways_from_json` parse the array entry-by-entry, dropping (with `log::warn!`) any that fail (unknown `app`/`kind`, corrupt row); `Gateway.bindings` uses `#[serde(deserialize_with = "lenient_vec")]` so an unknown-app binding drops just that binding, not the whole gateway. IPC commands with a providers-**list** arg (`provider_active_state(s)`, `activate_provider`, `deactivate_provider`) take the `ProviderList` newtype (lenient `Deserialize`) instead of a bare `Vec<Provider>` — otherwise one unknown entry fails the whole call at Tauri's arg-binding layer BEFORE the handler runs (the original `unknown variant 'grok'` bug). Single-provider args (`delete_provider`/`test_provider_api`/`fetch_provider_models`, activate's primary `provider`) stay strict — you're acting on exactly that one. The tray reads through `providers_from_json` too. Tests: `providers::tests::{providers_from_json_skips_unrecognized_entries_keeps_the_rest, gateway_with_unknown_binding_survives_keeping_known_bindings}`.

Termory does **not** store an "active provider" pointer anywhere. `provider_active_state` reverse-derives the active state on every read by parsing the CLI's live config files and matching against the in-memory provider list — this keeps Termory consistent when other tools (`cc-switch`, manual `vim`, the CLI's own OAuth flow) change the same files.

**Editing a live provider re-applies it.** Saving the editor (`saveProvider` in `ProvidersPage.tsx`) writes providers.json AND, when the edited provider is the one currently live for its CLI (matched for single-slot, or an enabled OpenCode slot), re-runs `activate_provider` so the change (model / base URL / key / options / …) reaches the live config — otherwise the edit would silently not take effect until a manual re-activate. It passes the *previous* provider copy into `providersForApp` too, so option keys the edit **removed** are still in the strip set and get cleaned (single-slot); for OpenCode the block is rebuilt wholesale so removal is automatic. If the OpenCode provider was also the startup default, it re-runs `set_opencode_default` to refresh the `model` pointer. New or inactive providers don't touch any live config.

`Provider` schema (in `providers.json`, fields default to omitted when empty):

```
{ id, app: "claude"|"codex"|"gemini"|"opencode", kind: "custom"|"official",
  name, baseUrl?, apiKey?, model?,
  npm?,            // OpenCode only — the AI SDK package, e.g. "@ai-sdk/openai-compatible"
  models?: [{ id, name }],  // OpenCode only — extra models for the picker (alongside primary `model`)
  options?: [{ key, value }] }   // "Advanced settings" — extra config entries merged into the CLI config
```

`config.ts` strips `""`/`null`/`undefined` top-level fields when writing providers.json, so an unfilled field is simply omitted. The two OpenCode-only fields are flat (no nested `opencode` block): `npm` is the official `provider.<id>.npm` package name written verbatim to opencode.json (defaults to `@ai-sdk/openai-compatible` when omitted — the editor drops it when left at the default); `models` is a list of extra models (`{ id, name }`, Rust `Vec<ProviderModel>`) surfaced in OpenCode's picker alongside the primary `model` — each written as `models[id] = { name }` (name defaults to id when blank); the editor renders it as add/delete ID+name rows. The **primary `model` is written first** in the `models` map — this relies on `serde_json`'s `preserve_order` feature (enabled in `src-tauri/Cargo.toml`), which makes ALL Termory JSON writes keep insertion order instead of alphabetizing (so merges into user configs also preserve the user's existing key order, and tool-arg renders like OpenCode `Read`'s `[offset, limit]` stay in source order). (note: `model` = primary id, `models` = the extras list). There is **no** `claude` block — Claude's per-size `/model` routing (`env.ANTHROPIC_DEFAULT_{HAIKU,SONNET,OPUS}_MODEL`) is expressed through `options` (those keys are deliberately NOT in `override_key_is_managed`, so they pass through; append `[1m]` to a value for the 1M context window). The editor seeds a fresh Claude provider's `options` with those three keys as a protected template (read-only key, no delete) and blocks save on **duplicate keys** or **managed keys** (`isManagedOptionKey` in `provider-utils.ts` mirrors `override_key_is_managed` — keep the two in sync; a managed key would otherwise be silently skipped at write time). The persisted field is `options`; the Rust struct field is `Provider.options: Vec<ProviderOption>` and the mechanism helpers keep their `override_*` / `apply_*_overrides` names since they still describe merging-and-overriding the CLI config.

### Codex "follow sessions" on provider switch (Codex-ONLY)

**The problem this solves — Codex-specific.** Codex tags every thread with the `model_provider` active at creation, and `codex resume` lists ONLY threads whose `model_provider` equals the CURRENT config provider (`resume_picker.rs` `picker_provider_filter` → `MatchDefault(config.model_provider_id)`). So after Termory switches Codex to a custom platform (provider id `termory`), a project's prior official-era sessions (`openai`) vanish from `codex resume`. **No other CLI has this** — Claude/Gemini/OpenCode list resume history by project/path, not by provider, so switching the API endpoint never hides sessions. The "follow" feature exists for Codex alone; the other CLIs' switch paths do nothing extra. (Verified: the installed Claude 2.1.175 binary's resume filter checks only `isSidechain`/`teamName`/`sessionKind`/`entrypoint`/`isLoopSession` — no provider/account dimension. Codex memories are separately gated on official auth — `uses_codex_backend()`, false for api-key — so custom-API sessions can't generate new memories; that's a Codex limitation the follow feature does NOT address.)

**What "follow" does (`src-tauri/src/codex_follow.rs`).** At Codex switch time the user picks which projects' sessions should follow into the now-active provider bucket so `codex resume` finds them. For each selected project's live, non-target sessions it:
1. **Rewrites the rollout JSONL's first-line `payload.model_provider`** to the target — this is the AUTHORITATIVE source. The `threads` table is only a CACHE: Codex rebuilds each row's `model_provider` from the rollout file's `session_meta` on startup backfill / resume reconcile (`state/src/extract.rs` `apply_session_meta_from_item`; upsert with no COALESCE guard at `runtime/threads.rs:754`). **Editing the table alone is silently reverted the moment Codex runs** — this was the original bug. The rewrite streams the (100+ MB) remainder unchanged, atomic temp+rename.
2. **Updates `threads.model_provider`** for the same rows (immediate visibility before the next backfill re-derives the same value).
3. **Restores the original file mtime** after the rewrite. The resume picker shows each session's time from the rollout file's MTIME (not `threads.updated_at`), so a naive rewrite makes every session read "just now" and destroys chronological order. Durability does NOT depend on the mtime (table is updated directly; reconcile re-reads file content).

**No journal / no per-session bookkeeping (deliberate).** The official bucket is ALWAYS `openai` (official subscription AND official api-key both default to it; `login_with_api_key` never sets `model_provider`) and Termory's custom bucket is ALWAYS `termory`. So the fold target is fully determined by switch direction — switching to Official → `openai`, to a custom provider/gateway → `termory`. Reversal is the symmetric switch-back (fold to the other fixed target), exactly like Claude project migrate, which also keeps no journal. An earlier versioned change-journal (`codex-changes.json`) was built then **removed** as over-engineering once the two-fixed-target invariant was confirmed — do not reintroduce it without a new requirement. (cc-switch's legacy `custom` bucket folds one-way into `openai`/`termory` along with everything else; it's just another non-target id.)

**Safety / rollback.** Opens RW with a 1.5s `busy_timeout` and surfaces a clean "database is locked — quit Codex" error (no write) when Codex holds the lock; per-file rewrites are atomic (temp + rename, original mtime restored) and only successfully-rewritten files get their table row updated, so a partial failure self-heals (Codex's backfill re-syncs the table from the files). No DB backup is taken — the `threads` table is a self-healing cache (snapshotting it protects nothing), and rollout files aren't individually backed up either (single-field atomic change); rollback is the symmetric switch-back.

**UI flow (`ProvidersPage.tsx` + `CodexFollowDialog.tsx`).** Only an official↔custom transition changes the bucket (custom→custom stays `termory`), so the prompt fires ONLY then (`effectiveActiveId === null` ⇒ official→custom for `setAsDefault`/`activateGateway`; `!== null` ⇒ custom→official for `setOfficialAsDefault`). **The Gateways tab also triggers it** (BOTH directions): `GatewaysPage.activateBinding` / `deactivateBinding` write to the CLI directly and would otherwise skip the prompt, so for a Codex binding on a bucket-changing switch they route through `ProvidersPage.codexFollowForBinding(direction, label, activate)` (a thin wrapper over `maybePromptThenActivate`, passed down as a prop) — `"toCustom"` on activate when Codex is Official (`activeStates.codex.kind === "official"`), `"toOfficial"` on deactivate when Codex is custom/unmanaged (turning the binding off folds Codex back to `openai`). The dialog is rendered once at the ProvidersPage root regardless of which tab is open. `maybePromptThenActivate` fetches `recent_codex_projects(0)` (limit 0 = no cap, newest-first, dialog scrolls), filters to projects with a session whose provider ≠ target; if none, activates directly with no prompt. On confirm the order is **activate first → toast → then migrate → toast** (activation returns a bool; migration only runs if it landed). The dialog uses the stock shadcn `Dialog`; project rows are raw `<button>` toggles with a `Check` icon (no shadcn Checkbox exists; raw rows are the project convention) and default UNCHECKED. Two actions: **"Activate only"** (`followSkip`, always enabled — switch the provider, migrate nothing) and **"Activate & keep"** (`followApply`, **DISABLED until ≥1 project is checked** — with nothing checked it would be identical to "Activate only", so the keep action requires a selection). IPC: `recent_codex_projects(limit)` + `follow_codex_sessions(projects, target_provider_id)` (lib.rs). Tests: `codex_follow::tests::*` (backend) + `GatewaysPage.test.tsx` (both follow directions fire from the Gateways tab; custom→custom does not; + delete-cleanup keep-on-failure) + `CodexFollowDialog.test.tsx` (keep gated on a selection).

**Memories do NOT need this (no feature) — verified in source.** Codex memories live in `~/.codex/memories_1.sqlite` (`stage1_outputs`, keyed by `thread_id` with an FK to `threads`; migration `0006_memories.sql`) — there is NO `model_provider`/account column, so they are NOT provider-bucketed and switching provider never hides them. The follow feature touches only `threads.model_provider`, never memories. Injection is LOCAL and UN-gated: `ext/memories/src/extension.rs:32` enables on `config.memories.use_memories` (default true) + `Feature::MemoryTool` with NO `uses_codex_backend()` check, and `local.rs` reads sqlite + `memory_summary.md` with no network — so under a custom-API (api-key) login EXISTING memories are still injected. Only GENERATION/consolidation is auth-gated (`memories/write/src/guard.rs:17` `uses_codex_backend()` is false for api-key, so phase1/phase2 are skipped), meaning no NEW memories grow under a custom provider — a Codex backend limitation, not a "hidden by provider" problem, so no Termory feature applies.

### Gateways — a SECOND, independent kind of provider management

Additive feature; does NOT touch the per-CLI provider management above. A **gateway** is ONE `{baseUrl, apiKey}` that may speak several API *modes*; you add it once, Termory auto-detects which modes respond, and you **bind** it to the CLIs whose required mode matches. One gateway → many CLIs (one key, edit once). Design recorded in the `gateway-station-provider-design` memory.

- **Storage (`PROVIDERS_SCHEMA_VERSION = 1`):** gateways live in the **UNIFIED `providers` array** of `providers.json`, discriminated by **`kind: "gateway"`** (alongside per-CLI providers whose `kind` is `"official"`/`"custom"`) — "a gateway is a kind of provider." A gateway carries `{ kind:"gateway", id, name, baseUrl?, apiKey?, capabilities?, bindings[], favicon? }`. `config.rs` keeps ONE `providers[]`: `read_providers()` returns entries `kind != "gateway"`, `read_gateways()` returns `kind == "gateway"`, and each writer preserves the other kind (`entry_is_gateway` filter). No migration from the old v2 separate `gateways[]` array — old data is dropped (per project rule). Frontend IPC names are unchanged (`read_app_gateways`/`write_app_gateways`); `write_gateways` injects `kind:"gateway"`, and `isGatewayList` requires it.
- **API mode ↔ CLI mapping** (the binding gate): Claude → Anthropic Messages; Codex → OpenAI **Responses** (`wire_api="responses"`, needs the `/v1/responses` probe specifically); Gemini → Gemini API; OpenCode → any mode (npm SDK, one binding per supported protocol); Claude Desktop → Anthropic Messages (when `caps.anthropic`). `appProtocols(caps)` in `provider-utils.ts` computes the capability-bindable set; on top of that the **GatewayEditor install-gates every app** (`if (!installed[app]) protocols[app] = []`, `installed` threaded from ProvidersPage) so a binding is only offered for a tool you can actually run — mirrors the Providers tab.
- **Detection:** `detect_gateway_apis` (backend) probes the four modes concurrently; `GatewayCapabilities` carries per-mode `ok` + a model list (for the binding's model picker). Codex (protocol `"openai"`) reuses the `/v1/models` list since the Responses probe has none.
- **A binding is a provider minus the gateway's common fields, WITH its own id:** `{ id, app, model?, npm?, models?, options? }`. There is **no `protocol` field** — it's DERIVED via `protocolForBinding` (Claude→anthropic, Codex→openai, Gemini→gemini, OpenCode→`protocolForNpm(npm)`). The own id (vs the old `gateway:<id>:<app>`) lets one CLI hold several bindings and is the activation-marker key. `options` = advanced settings (Claude seeds the `ANTHROPIC_DEFAULT_{SONNET,OPUS,HAIKU}_MODEL` routing template); `npm` + `models` are OpenCode-only. `GatewayEditor` keeps an internal-only `BindDraft.protocol` for the model picker; `isGatewayList` rejects bindings without `id` so pre-refactor data drops (no migration).
- **Detection probes each capability at its OWN real API endpoint** (POST, empty-body route-exists `code≠404/405`) — a GET `/models` list NEVER gates a capability (only proves a list route exists → false positives). Naming mirrors OpenCode's AI SDK packages: `openaiCompatible`→`POST /v1/chat/completions` (`@ai-sdk/openai-compatible`), `openai`→`POST /v1/responses` (`@ai-sdk/openai`, **Codex**), `anthropic`→`POST /v1/messages`. **Gemini is the exception**: gated on `GET /v1beta/models?key=` returning data — that path is Gemini-SPECIFIC (a non-Gemini gateway 404s it, so data ⇒ support), unlike OpenAI's generic `/v1/models` which every compatible gateway answers. The same Gemini GET also feeds the `models` catalog (`fetch_models_list` returns `(got_data, models)`). `GatewayCapabilities` = **4 booleans + flat `models` catalog** (DATA-ONLY autocomplete, union of `GET /v1/models` + `GET /v1beta/models`; gateway routes by model id, no per-mode split). `GatewayProtocol` = `"openai-compatible" | "openai" | "anthropic" | "gemini"` (`protocolForNpm` matches `openai-compatible` before `openai`). `appProtocols`: Codex gates on `caps.openai` (Responses). `modelsForProtocol` + `ApiProbe` removed.
- **`capabilities` IS persisted** (now small — 4 booleans + one flat `models` catalog): `handleSave` writes `capabilities: caps`. Reopening a gateway shows the saved bindable sources + autocomplete immediately (rendered from the loaded `caps`); `lastTried` starts empty so opening the editor also **auto-redetects once** (when base URL + key are present) — mirrors ProviderEditor's model auto-fetch, so editing always refreshes the `models` catalog and shows a current "N models available", and `handleSave` persists the refreshed `caps`. Manual refresh / a base/key change re-probe too. A new gateway with no detection persists nothing (caps undefined → stripped).
- **Gateway base URL is stored PATH-LESS** (bare root, no API-version path): the editor strips a pasted `/v1` or `/v1beta` on save, and EACH CLI's real URL is DERIVED per protocol — `gatewayBaseForProtocol` reduces to the bare root then adds OpenAI `/v1`, Anthropic bare (Claude appends `/v1`), Gemini bare (it appends `/v1beta`). Detection mirrors this (`detect_gateway_apis` builds every probe URL from the stripped `root`; `join_v1` was removed). So a base entered as `…/v1` no longer breaks the Gemini path.
- **Activation reuses the existing path:** `providerFromBinding(gateway, binding)` (provider-utils) synthesizes the normal `Provider` shape — id = `binding.id`, base URL derived per the DERIVED protocol (`gatewayBaseForProtocol`), OpenCode `npm` + `models`, the binding's `options`, and `favicon = gateway.favicon`. That synth flows through `activate_provider` / `deactivate_provider` / reverse-derivation UNCHANGED. Editing a gateway re-activates its active bindings (mirrors `ProvidersPage.saveProvider`); deleting a gateway (or unbinding) `deactivate_*`s only the bindings that were actually active (marker + creds). A delete that can't clear a binding's live config (CLI running → DB locked) surfaces `toast.clearFailed` and **KEEPS the gateway** so it isn't silently lost while a CLI still points at its endpoint — mirrors `ProvidersPage.deleteProvider`; the retry is idempotent (already-cleaned bindings skip). When a standalone provider and a binding share identical creds (indistinguishable on disk), the per-CLI marker `active_provider_ids` (config.json) — honored only while its creds match the live snapshot — disambiguates which is "in use" via `resolveActiveProviderId`.
- **UI:** a separate **"Gateways" tab** in `ProvidersPage` (`view` state — `"providers" | "gateways"`, the tab value `"gateways"` is not a `CliApp`). `GatewaysPage` lists gateways (add/detect/bind via `GatewayEditor`, activate/deactivate per binding, delete). The per-CLI Providers list ALSO surfaces gateway bindings targeting that CLI as `ProviderCard`s with a `gatewayBadge` — **view + activate/test only, NO Edit/Delete** (those props are omitted, so `ProviderCard` hides the buttons; bindings are managed exclusively from the Gateways tab — by design). The synth provider carries `favicon = gateway.favicon` so the card shows the gateway's icon. `ProvidersPage.refreshActive` passes `[...providers, ...gatewaySynth]` so a gateway-activated CLI matches the synth id instead of reading "Unmanaged".
- **Tests:** `config::tests` (gateways roundtrip + providers↔gateways no-clobber), `providers::tests` (`parse_model_ids`), `provider-utils.test.ts` (`gatewayBaseForProtocol` incl. path-less/sub-path cases, `appProtocols`, `protocolForBinding`, `providerFromBinding`, `isGatewayList`). The HTTP probes themselves are network-bound (not unit-tested).
- **Tray** surfaces gateway bindings: each CLI submenu lists its bindings alongside standalone providers (the tray synthesizes them via `providers::gateway_providers` (read once, grouped per CLI) → `provider_from_binding`, the Rust mirror of the frontend `providerFromBinding`, and activates through the same `activate` / `read_active_state` path; only **installed** CLIs (`detect_install_snapshot`) get a submenu). **Known gap (not yet done):** `detect_gateway_apis` is best-effort (a permissive gateway can answer both OpenAI and Anthropic on `/v1/models`).

## Menu-bar tray (macOS system tray)

A native system-tray icon (the macOS menu bar) for quick provider switching, separate from the in-app Providers rail route. **Click model per OS:** on macOS (menu-bar item) left click opens the menu; on Windows/Linux the menu is on RIGHT click (`show_menu_on_left_click(false)`) and LEFT click (release) opens the app window — the platform convention. (Linux appindicator trays deliver no click events, so left-click-opens-window is effectively the Windows path.) Implemented in `src-tauri/src/tray.rs` and installed from `lib.rs` `setup()`. Requires the `tauri` features `tray-icon` + `image-png` (Cargo.toml).

**Menu shape** — "Open", then up to 5 recent session titles, then one submenu per CLI (the active choice shown inline on the first-level row; submenu lists Official + the user's providers + this CLI's gateway bindings, with the active one checkmarked):

- **Recent sessions + New session** — up to 5 most-recent session titles sit flat under "Open" (newest first by `updated_at`; Memory/Skill, slash-command and empty-id records excluded; label = title → snippet → "(untitled)", truncated) — a single click (`tray:session:{source}:{id}` — content-addressed, looked up by identity so a watcher rebuild while the menu is open can't resume the WRONG session; missing → silent no-op) **launches a fresh OS terminal**, `cd`s into the session's cwd (when that dir exists) and resumes via **`terminal::resume_session(source, id, project)`** — the SAME entry point the Records / Favorites right-click "Resume in terminal" uses. Below the sessions one localized **"New Session" SUBMENU** lists the first 5 distinct project cwds in the same recency order (dedup ACROSS CLIs; empty-cwd records skipped) as NESTED submenus (cwd basename), each holding one row per INSTALLED CLI, ordered by which CLI was last used in THAT project (cli_recency — most likely choice on top), then the rest (flat header+rows grew too long) — picking a row (`tray:new:{cliKey}:{full project path}` — the path rides in the id, fully decoupled from RECENT; the `tray:newpick:` dispatch check must stay FIRST since it shares the prefix) calls `terminal::new_session(cli_source(cli), project)`: the chosen terminal opens in that cwd and that CLI launches fresh (any installed CLI, not just the ones with history there). A **"Choose Folder…"** tail submenu (`tray:newpick:{cliKey}`, localized `tray.chooseFolder`) opens the native directory picker (tauri-plugin-dialog `pick_folder`, async callback) and launches the picked CLI fresh in the chosen dir — works for brand-new directories and keeps New Session present with zero history (whole submenu skipped only when no CLI is installed). Both halves are computed by `select_recent_state` into `static RECENT: Mutex<RecentState>`, refreshed by `tray::refresh_recent(app, &records)` from the **existing** scans (the `scan_all_sessions` IPC + the watcher) — the tray never scans on its own, and the update is skipped when nothing changed. The refresh splices the dynamic region IN PLACE (`update_recent_region`: `Menu::remove_at`/`insert_items` over the cached root handle + region length in `RECENT_REGION`; region = items from `build_recent_region`, shared with build_menu, starting at the fixed `REGION_START` = 2 right after "Open"+separator) — a full `set_menu` rebuild CLOSES an open menu on macOS, while in-place splicing updates the open menu live (user requirement: refreshes apply immediately AND never dismiss the menu). Any splice failure falls back to a full rebuild. ONE deliberate exception to "never dismiss": an installed-set change (CLI installed/uninstalled since the menu was built) forces a full rebuild even from the menu-open path — the splice can't refresh the per-CLI submenus, and a one-time dismissal beats a permanently stale CLI list (see "Install/uninstall auto-refresh" below). ALL menu mutations (rebuilds, the splice, quota title set_text) are QUEUED on the main thread via `run_on_main_thread` — the queue serializes concurrent refreshers (watcher thread + the scan_all_sessions IPC) that would otherwise interleave remove/insert ops or write a stale menu handle back; a mutex was rejected (worker-holds-lock-waits-main vs main-waits-lock deadlock). (An earlier per-project-submenu design — project rows each holding new+sessions — was tried and rejected: it added a hover step to the most-frequent action and produced duplicate same-named rows.) `resume_session` builds the command via `session_launch_command` (mirrors the frontend `resumeCommandFor` — all four resume by id: `claude --resume <id>` / `codex resume <id>` / `opencode --session <id>` / `gemini --resume <id>`; the session id is charset-guarded `[A-Za-z0-9._-]` before interpolation — injection defense), reads the user's **Settings → Terminal** choice (`terminal` config key; empty / `"auto"` → the OS default), and calls `terminal::open(choice, project, cmd)`. `terminal::detect()` (the `detect_terminals` IPC) lists the mainstream terminals found installed per-OS (macOS: Terminal/iTerm/Ghostty/Alacritty/Kitty/WezTerm; Linux: GNOME/Konsole/XFCE/Alacritty/Kitty/WezTerm/xterm; Windows: Windows Terminal/PowerShell/cmd) — only macOS is verified, Linux/Windows best-effort.
  - **Cold-launch single-window (macOS GUI terminals).** Terminal.app and iTerm are activated via AppleScript (`terminal_app_script` / `iterm_script`), and a naive `activate` + `do script` / `create window` opens TWO windows when the app wasn't already running (the launch's default empty window plus the command's). The builders guard against this: already running → a fresh window; cold launch → reuse the window the launch creates (Terminal: `do script … in window 1`; iTerm: a delay-guarded `count of windows` check that writes into the launch window, else makes one). Asserted by `terminal::tests::{terminal_app_script,iterm_script}_reuses_launch_window_on_cold_start` — don't revert to the bare `activate`+`do script` form. The CLI-launched terminals (Ghostty via `open -na`, Alacritty/Kitty/WezTerm and ALL Linux/Windows terminals) spawn one window per invocation, so they don't have this issue.
- **Recent-session live work status (Claude-only)** — a currently-running Claude session's row shows its live status after the title: `{title} · Working` / `{title} · Needs input` (idle / not-running rows show just the title). **Plain text, no glyph** — a native macOS menu is an all-text list, so a colored dot would mean either an emoji (cheap) or a far-left icon column (breaks the otherwise icon-less menu); the word alone stays clean. Source is Claude's OWN native runtime file `~/.claude/sessions/<pid>.json` (respects `CLAUDE_CONFIG_DIR`) — the snapshot it writes for `claude ps`, NOT the transcript and NOT a hook (so Termory reads it in place). Verified against Claude source: `utils/concurrentSessions.ts:19` `SessionStatus = 'busy' | 'idle' | 'waiting'` (+ `waitingFor` detail), derived in `screens/REPL.tsx:1605`. `sessions::claude_work_statuses()` → `claude_work_statuses_in` reads the dir → `parse_claude_status_snapshot` maps `busy`→Busy, `waiting`(unless `waitingFor == "dialog open"`, the user-opened-UI case)→Waiting, and `idle`/terminal `state`/missing → no entry (prefers the richer `state` field — working/blocked — when present, else `status`+`waitingFor`). Files are filtered by Claude's exact filename guard `^\d+\.json$` (all-ASCII-digit stem; the `2026-…_notes.md`-as-pid bug, anthropics/claude-code#34210), a **PID-liveness probe** (`process_alive`: `libc::kill(pid, 0)` on unix via `[target.'cfg(unix)'.dependencies] libc`, `OpenProcess` on Windows via `[target.'cfg(windows)'.dependencies] windows-sys`, conservative `true` on exotic targets; mirrors Claude's `isProcessRunning`, so a crashed session's residual busy file isn't shown — mtime alone can't tell a long-busy live session from a crashed one), and a 24h-mtime **PID-reuse backstop** (`CLAUDE_STATUS_MAX_AGE`). Joined onto recent rows by `id == sessionId` (Claude rows only) in `tray::attach_work_statuses`; the FS read runs on `refresh_recent`'s caller thread (off the main thread), and `RecentSession.status` feeds `work_status_label` at render time in `build_recent_region`. **Refresh is event-driven, no timer:** a live status change rewrites the `<pid>.json` under the recursively-watched `~/.claude/`, so the watcher's `refresh_recent` reflects busy↔idle↔waiting promptly. A CRASH (kill -9) leaves the file untouched — no filesystem event — so the tray click (`on_tray_icon_event`) ALSO calls `tray::refresh_work_status`, which re-runs the liveness probe against the CACHED recent list (no session scan — only re-reads `~/.claude/sessions/` + re-attaches) and re-splices, clearing a crashed session's stale status on the next menu open. `refresh_recent` + `refresh_work_status` share `installed_cli_list` + `commit_recent` (store-if-changed → in-place splice → full-rebuild fallback, queued on the main thread). Status text is localized via the tray-labels push (`tray.statusBusy` / `tray.statusWaiting`). **Caveat:** the `status` field is written only when Claude's `BG_SESSIONS` feature is on (`REPL.tsx:1623`); with it off the file has no status → no work status surfaces (graceful degradation). Other CLIs have no equivalent live-status file, so this is Claude-only — and that's a hard limit, not a missing feature (cc-status is Claude-only for the same reason). **Codex (verified, don't re-investigate):** its live session state lives in the app-server **daemon, in-memory**, reachable only over an IPC socket (`app-server/src/thread_state.rs` — `Arc<CodexThread>` + listeners), NOT on disk; `~/.codex/sessions/` holds only rollout JSONL (history), the `threads` table in `state_5.sqlite` has NO status/active/pid column, and the one daemon `pid.rs` file is a single `{pid, processStartTime}` for the app-server process (not per-session). The only disk-derivable Codex signal is rollout-file mtime = "recently active", which can't distinguish busy/waiting/idle and reads identical for an idle-but-running session vs a closed one — misleading, so NOT used. Real Codex status would require speaking the daemon's IPC protocol (a live socket client, not a file read) — out of scope. **Gemini / OpenCode** likewise write no per-session run-status file. Tests: `sessions::tests::{parse_claude_status_snapshot_maps_running_states, claude_work_statuses_in_filters_by_filename_and_liveness}`, `tray::tests::{attach_work_statuses_joins_claude_rows_by_id_only, work_status_label_maps_states}`.

Each window carries a pressure emoji (`quota_glyph`: <75% 🟢, ≥75% 🟡, ≥90% 🔴 — thresholds are `quota::{WARN_PCT,CRIT_PCT}`, mirrored by `QUOTA_WARN_PCT`/`QUOTA_CRIT_PCT` in src/lib/quota-utils.ts for the app's ring); emoji because macOS menu text can't be colored. Suppressed while a custom provider is active — the quota belongs to the official login, so gluing it onto a custom provider's name would misread as that provider's usage. Cached per quota-capable CLI (`quota::SUPPORTED` — the backend's single support list; frontend mirror `QUOTA_SUPPORTED` in ProvidersPage.tsx) in `static QUOTA: Mutex<Vec<(CliApp, TrayQuota)>>`; updated by `tray::refresh_quota` from THREE triggers (NO periodic polling): a one-shot warm-up at startup (`trigger_quota_refresh` in `setup()`), every tray-icon click (= menu open, via `on_tray_icon_event` — rate-limited per CLI to one fetch per 2 min (60s after a failure) via `QUOTA_LAST_FETCH`, which `refresh_quota` updates on EVERY completed fetch — including the Providers page's IPC — so page and tray share one rate limit; the fetch lands after the menu is showing; the changed numbers are applied IN PLACE via `Submenu::set_text` on cached `CLI_ROWS` handles (`update_cli_row_title` / `cli_row_title`) — a full `rebuild_menu`/`set_menu` here CLOSED the open menu on macOS), every COMPLETED `fetch_subscription_quota` IPC (success or failure — a Providers-page refresh updates the tray, the shared marker, and the not_found clearing with no extra network hit), and the filesystem watcher: a change to a CLI's credential file (`.credentials.json` → Claude, `.codex/auth.json` → Codex, `.gemini/oauth_creds.json` → Gemini; the path→CLI map is `quota::credential_cli_for_path`, single-sourced next to the credential readers — watcher.rs just delegates) calls `tray::force_quota_refresh` — bypasses the normal floors (10s burst-dedup only) so login/logout reflects near-instantly (Keychain-backed creds emit no file event; the 60s not_found retry is the fallback). Every completed fetch is ALSO pushed to the frontend via the `termory:quota-changed` event (payload = `SubscriptionQuota`; const `quota::QUOTA_CHANGED_EVENT`, mirrored in src/constants.ts) so an open Providers page reflects backend-initiated fetches without its own request. A `not_found` result (logged out — definitive, unlike transient failures) CLEARS that CLI's tray quota entry instead of keeping stale numbers; likewise a SUCCESSFUL fetch with no usable windows — logged in but with no active subscription, where `/api/oauth/usage` returns windows whose `utilization` is null/absent (verified against the official CLI: `services/api/usage.ts` types `utilization` as `number | null` and `Settings/Usage.tsx:218` shows "/usage is only available for subscription plans" precisely when no window is present) — clears the entry, so a cancelled-subscription account doesn't keep showing stale percentages. Other failures keep the last good numbers; the title update is skipped when unchanged. Quota changes never trigger a full rebuild while running (set_text only; full rebuilds still happen on provider mutations / recent-list changes / label pushes / installed-set changes).
- **Active state is reverse-derived** via `providers::read_active_state` (same as the Providers page) — Termory still stores no "active provider" pointer. Checkmark + inline `· name` use the matched provider name, else "Official".
- **CLI display names** match the Providers page tabs (`CLI_APP_LABEL` in `src/constants.ts`) — keep `cli_label` in `tray.rs` in sync (it's "Gemini", not "Gemini CLI").
- **Static row labels are localized** (Open / Official / Exit). The tray is Rust (built in `setup()` before the frontend loads, so it can't read the i18n dicts), so the FRONTEND pushes the translated strings: an `App.tsx` effect (deps `[t, localeReady]`) calls the **`set_tray_labels(open, official, exit, fiveHour, weekly, monthly, newSession, chooseFolder, statusBusy, statusWaiting)`** IPC on language load/change → `tray::set_labels` stores them in a `static TRAY_LABELS: Mutex<Option<TrayLabels>>` (English default) → `rebuild_menu`. CLI / provider names stay untranslated (brand / user data). Keeps i18n single-sourced in the frontend dicts (no Rust translation table to drift). `tray.open` / `tray.official` / `tray.exit` / `tray.newSession` / `tray.chooseFolder` / `tray.statusBusy` / `tray.statusWaiting` keys (+ the quota row reuses `providers.quotaFiveHourShort` / `providers.quotaSevenDayShort` / `providers.quotaMonthlyShort` (30_day → "Monthly")). **The push is gated on `useI18n().ready`** — `<I18nProvider>` starts `ready=false`, flips it `true` (via `.finally`) once the saved `language` config has loaded, so the tray gets ONE push with the FINAL locale instead of first flashing the `navigator`-guessed one (the provider seeds from `navigator.language`, then the async config override wins; without the gate the tray briefly showed the system-guessed locale). `ready` defaults `true` in the no-provider context so isolated component tests are unaffected.
- **Click handler** reuses the same write helpers as the IPC commands (`activate` / `deactivate`), so the on-disk path is single-sourced. For **OpenCode** a click does `activate` **+** `set_opencode_default` (the slot must exist before it can be the default — `set_opencode_default` errors otherwise), so one click both enables the slot and sets it as default, matching the Providers page end state. Single-slot CLIs (Claude / Codex / Gemini) need only `activate`.
- **Menu is rebuilt** (`tray::rebuild_menu`) after every tray click and after the five provider-mutating IPC commands (`activate_provider` / `deactivate_provider` / `delete_provider` / `set_opencode_default_provider` / `write_app_providers`) so the checkmarks / inline titles stay in sync.
- After a tray switch the handler emits **`termory:providers-changed`**; `ProvidersPage` listens for it and re-derives active state, so an open Providers page reflects a tray switch even when unfocused.
- **Open / Exit** are plain `MenuItem`s (not `PredefinedMenuItem::quit`) so macOS attaches no native item icon. Exit calls `app.exit(0)`.
- **Icon**: embedded `icons/tray-icon.png` (36×36 = 18pt @2x, the macOS standard), a pure-black template image of the three-card terminal "chip" from the app icon, optically centered. On **macOS** it's marked `icon_as_template(true)` so the bar themes it for light / dark; on **Windows / Linux** the tray instead uses the COLORED app icon (`default_window_icon`) — a monochrome template reads as a black blob in those system trays, which don't do menu-bar theming. `icons/tray-template.svg` is the vector source; the menu-bar size is governed by the whole image (tray-icon crate scales it to a fixed 18pt height), so the artwork's transparent margin controls how large it reads.

Only **installed** CLIs get a submenu — callers probe `detect_install_snapshot()` (the same probe as the Providers page's `detect_clis`; the snapshot = installed map + `codex_terminal`, see the `detect_codex_installs` bullet) and `build_menu` skips any CLI not found, so the tray lists only what you can actually switch. **Install/uninstall auto-refresh:** `static INSTALLED` caches the install snapshot the VISIBLE menu reflects — stored only AFTER a successful `set_menu` (`do_rebuild_menu_with`) / tray `install()`, never inside `build_menu` (an early store would let a failed rebuild claim the new set and permanently kill the staleness check; on failure the cache keeps the old set so the next refresh retries). `rebuild_if_installed_stale` (main-thread, the single owner of the compare→rebuild step) is fed by three probe paths, each probing on ITS OWN thread and passing the snapshot along so nothing re-probes on main: the watcher's install-detection branch (the same one that emits `cli-install-changed`) calls `tray::refresh_installed`, which RETURNS the probed snapshot so the same burst's rescan reuses it via `refresh_recent_with` (one PATH probe per burst, not two); the `detect_clis` IPC (Providers-page Recheck) hands its result to `tray::refresh_installed_with`; and the shared `commit_recent` path (fed by `refresh_recent` + the tray-click `refresh_work_status`) does the same compare, so an install missed by the watcher self-heals on the next menu open / scan. A stale snapshot (including a `codex_terminal` flip — the standalone CLI installed/removed while the desktop app stays) forces a FULL rebuild (not the recent-region splice — the splice can't refresh the per-CLI submenus; this is the documented exception to "never dismiss the menu" above). **Claude Desktop is covered too:** its install marker is the config dir itself (`claude_desktop::is_installed`), which can't be watched before it exists — so the watcher watches the PARENT dir(s) (`claude_desktop::install_watch_parents()`, derived from the same `config_parent_dir()` helper `current_paths` uses: `~/Library/Application Support`; on Windows the candidate parents incl. the MSIX `Packages\` dir, non-recursive) and `event_touches_claude_desktop` (watcher.rs) filters events to direct children matching `claude_desktop::is_install_marker_name` (the `Claude*` rule, owned next to the Windows dir resolution so it can't drift) before routing them into the same install-changed branch. Those parent dirs are busy shared dirs, so their direct-child events are ALSO excluded from the session-rescan gate (`event_has_relevant_path` takes the parents as an ignore list) — otherwise every other app's activity there would trigger a full `scan_sessions`. **Claude Desktop** is included in the per-CLI provider-switch loop (its own `installed` gate via `claude_desktop::is_installed`, `cli_label`/`cli_key` arms) so it gets a switch submenu when installed, but it is **excluded from the terminal flows** (recent-session resume + "New Session"): those filter on `CliApp::is_cli()`, which is false for the GUI app. It has no quota row (`quota::SUPPORTED` excludes it).

**Known minor gaps (by design for a quick-switcher):** the tray doesn't expose OpenCode's multi-slot enable/disable or delete; failures are `log::error!`-only (no toast). The **provider** checkmarks/inline titles refresh only on Termory-initiated changes, so an external switch (cc-switch / manual edit) can leave them stale until the next Termory action. The **recent-projects** list does refresh on the filesystem watcher (and every `scan_all_sessions`), so it stays current with on-disk session changes.

### Window / Dock behavior (menu-bar app)

**Single instance:** `tauri-plugin-single-instance` is registered FIRST in the plugin chain (per its docs) — a second launch (double-clicked exe on Windows; macOS bundles are natively single-instance) surfaces the running instance's window via `tray::show_main_window` and exits.

Closing the window does **not** quit — `lib.rs` `on_window_event` intercepts `CloseRequested`, calls `tray::hide_main_window` (window.hide + macOS `set_dock_visibility(false)`) + `api.prevent_close()`, so the app keeps running in the menu bar with no Dock icon. The tray's **Open** restores the Dock icon (`set_dock_visibility(true)`) then shows / unminimizes / focuses the window. The window is declared `visible: false` in tauri.conf.json; a NORMAL launch shows it in `setup()` (`tray::show_main_window`), while a login-item launch (`--autostart`) stays tray-only (the Dock icon is suppressed PRE-RUN via `app.set_activation_policy(Accessory)` before `app.run()` — a setup()-time `set_dock_visibility(false)` was too late and flashed the icon) — declaring it hidden is what stops the window flashing before setup() runs. `hide_main_window` / `show_main_window` (tray.rs) are the shared hide/show pair used by close-to-tray, --autostart, and the tray's Open. `set_dock_visibility` is the purpose-built API — a raw `set_activation_policy(Accessory)`/`Regular` toggle did NOT reliably restore the Dock icon when re-showing the window.

The window's title-bar **text is hidden** (`"hiddenTitle": true` on the window in `tauri.conf.json`) — the traffic-light buttons and a normal draggable title bar stay; only the "Termory" label is suppressed. `title` is still `"Termory"` so Mission Control / the window menu identify it.

The three fixed brand anchors (claude/gemini/openai) crowd the hue space, so the six added ones are brand-ADJACENT distinct hues (gold≈Mistral, violet≈DeepSeek, magenta≈Qwen, crimson=Grok, indigo≈GLM-blue, rose≈MiniMax-coral) rather than exact logos — with nine families past the CVD-safe ceiling, distinctness is the hard requirement and brand a lean (user call). Unknown-provider ids (an exotic custom / gateway model — rare now that the nine mainstream vendors are covered) fall to a two-hue neutral pool (`EXTRA_MODEL_COLORS` = cyan + slate, the only hues left ≥ ΔE 8 from all nine anchors), then the Others grey. Color tracks each model's ALL-TIME rank (StatsPage's `globalModelRank`), so a source/range filter change never repaints the survivors.

### Accuracy rules (LOCKED — do not weaken)

All Stats values are **window-accurate** — they reflect what actually happened in the chosen date range, NOT lifetime totals.

| Metric | Source | Notes |
|---|---|---|
| Sessions | `started_at ∈ window` count | Old session reused today does NOT count |
| Messages | `Σ daily_tokens[date ∈ window].messages` | Per-message timestamps from backend |
| Tokens | `Σ daily_tokens[date ∈ window].tokens` | Same |
| Active days | window days with `messages>0 ∨ tokens>0` | From `dailyTokens` buckets |
| Streaks | consecutive active days (`overviewKpis`) | current = run ending at the window's last day, with a one-day grace (not-yet-active today counts back from yesterday); longest = max run |
| Peak hour | argmax of in-window `daily_tokens.hours` sums | null (— shown) with no hourly data |
| Favorite model | `overviewKpis().favoriteModel` — top model by in-window tokens, skipping "Unknown" | session-level attribution |

**No fallback smearing**: a session with `s.tokens` but no `s.daily_tokens` contributes ZERO to Messages/Tokens — Termory does not even-distribute lifetime totals across days (that would fabricate per-day numbers indistinguishable from real ones).

**filter uses interval overlap**: `filterSessions` keeps a session if `[started_at, updated_at] ∩ window ≠ ∅` — filtering on `updated_at ∈ window` alone would drop sessions whose window contribution predates their last update.

**`all` range**: `resolveRange(range, sessions)` — starts at the earliest `daily_tokens` date (fallback `started_at`); with no datable activity it degrades to the 30d window. `to` is always end-of-today so sessions still being written stay in the filter.

**Cross-source consistency** (backend-guaranteed, test-pinned): `Σ dailyModelTokens.series[*][d] === dailyTokens[d].total` for every date — the stacked chart's per-day totals reconcile exactly with the daily rollup (the "Unknown" bucket rides inside "Others" in the chart precisely so this holds while the legend keeps hiding Unknown).

### Model attribution is session-level (approximate)

`AppSession.model` is one best-guess id per session, so `dailyModelTokens` (stacked series + the legend's input/output split) and `overviewKpis().favoriteModel` attribute a session's whole token contribution to its single recorded model — a session that switched models mid-run lands entirely under its main model. Sessions with no recorded model bucket under `"Unknown"`, hidden in the legend/KPIs but folded into the chart's Others bucket (see cross-consistency above). True per-message model splits would need a backend `daily_tokens` model dimension — deliberately not built (approximation accepted by design decision, 2026-07).

### Calendar heatmap intensity (LOCKED rationale carried over)

Day cells use the SAME weighted-geometric-mean rule as the retired 24h heatmap, at day granularity: `ratio = m^0.6 · t^0.4` (m/t = messages/tokens normalized to the window max), with single-dimension degradation (no tokens anywhere → messages-only; no messages → tokens-only) and the same low-skewed tier thresholds (0.08/0.18/0.35/0.55/0.75 → `bg-primary/25…100`; truly inert → `bg-foreground/[0.08]`) — the calendar bumps each tier ~10% darker than the retired 24h grid's `/15…90`. The rationale (messages alone under-light "one big request" hours, tokens alone under-light "many short messages") is unchanged — see git history of `DailyActivitiesHeatmap.tsx` if it needs re-deriving. The heatmap ALWAYS spans the full history (earliest activity day → today, following the source filter but NOT the All/30d/7d range — that scopes only the KPIs + Tokens chart), like a GitHub contribution graph. Weeks render left→right oldest→newest with a GitHub-style top month axis (label on each month's first column) and a left weekday axis (Mon/Wed/Fri, fixed while the grid scrolls); leading/trailing padding cells share the empty-day grey so the grid is one full rectangle, and it scrolls horizontally auto-scrolled to the newest week.

### Frontend aggregation

**One statistics function per UI module (LOCKED alignment).** `src/lib/stats-utils.ts` exposes exactly **one aggregator per Stats module**, plus the shared window/filter setup — the 4 modules map 1:1 to 4 functions:

## Favorites

Per-message starring + dedicated Favorites route. Stars live next to every message in the Records detail pane; the Favorites route lists them in a Records-style 2-column shell (list / detail) and survives source-file deletion via local snapshots.

### Snapshot rule (LOCKED — do not weaken)

A `Favorite` is a **self-contained snapshot** of the parsed message. The full `SessionMessage` (role + complete markdown text + timestamp + kind) gets stored verbatim alongside source-session metadata (title, project, path, message index). When the source session is later deleted / renamed / re-parsed differently, the Favorite **stays readable and renders identically** — the detail pane uses the same `<MessageBody>` (react-markdown + remark-gfm) pipeline as the Records detail, so what you see in Favorites matches what you saw when you starred it.

Do not:
- Replace the snapshot with a `(source_session_id, message_index)` reference that re-fetches the message at render time. The "Open original" button still uses that tuple, but as a navigation hint, not the source of truth. If the index has drifted by the time the user clicks it, that's accepted — the snapshot in the favorite is authoritative.
- Strip the snapshot to "just the markdown text" — `role` / `kind` / `timestamp` are read by the role-bar color, the lowercase chip, and possible future tooltips.
- Lazy-fetch session metadata. `source_session_title` / `source_session_project` are stored at favorite time so the list card still has something to show when the original session is gone.

### Wire shape

`Favorite` (per favorite, in `~/.termory/favorites.json` as a JSON array):

```ts
{
  id: string;                     // UUID v4 (frontend-generated)
  favorited_at: string;           // ISO 8601 UTC
  message: SessionMessage;        // full snapshot
  source: SessionSource;          // narrowed: "Claude" | "Codex" | "Gemini" | "OpenCode"
  source_session_id: string;
  source_session_path: string;
  source_session_title: string;
  source_session_project: string;
  source_message_index: number;
}
```

Same `SessionMessage` struct used by `scan_all_sessions` / Records — no schema duplication.

### Identity key

The `(source, source_session_id, source_message_index)` tuple is the "is this message currently favorited?" key (`favoriteKey()` in `src/lib/favorites.ts`). Used by:
- The star button to render its fill state in O(1)
- `toggleFavoriteEntry()` to flip between add / remove
- The `[&_*]:text-primary-foreground` highlight cascade in the list cards

Index drift across re-parses is the documented trade-off — if a session's `merge_tool_outputs` produces a different message at the same index later, the Records star may light up on the wrong message. The Favorites page itself is unaffected because it renders the snapshot. We deliberately did NOT pick a content hash because (a) it complicates "click star to remove" UX (hash mismatch ≠ "wasn't favorited") and (b) index drift is rare; sessions are append-only in all four scanners.

### Frontend layout (LOCKED for visual parity with Records)

FavoritesPage is the same shell as Records' middle + right columns:
- List column: `bg-sidebar` aside, 240–300px, `text-sidebar-foreground` default text, `bg-primary text-primary-foreground [&_*]:text-primary-foreground` active state — identical class set to Records' session list buttons. Newest first by `favorited_at`. Auto-selects the first card on mount and after the previously-selected card is removed.
- Detail column: same `<header>` shape as Records detail (`text-lg font-semibold` title, `text-xs leading-none` meta row with `·` chips, size=12 lucide icons). Action icons (`ExternalLink` / `Trash2`) cluster top-right of the meta row, NOT the title row — keeps the title clean.

`MessageList` (used in Records, optionally pluggable into anywhere else) accepts an optional `favorites: FavoriteContext` bundle (session + keys + onToggle). Caller that doesn't want the affordance simply omits the bundle — the three-field grouping prevents "forgot to pass one" bugs.

### Scroll-to-message navigation (shared by Favorites + Search + Cmd-K + in-session find)

Four sites navigate "into a specific message" — Favorites "Open original", Search results, Cmd-K palette results, and the in-session find bar's next/prev jumps. All converge on the same `openItem(item, messageIndex?, query?)` → `pendingScroll` → `MessageList scrollRequest` → `onScrolled` path (the find bar skips `openItem` and sets `pendingScroll` directly via `jumpToFindMatch`):

1. **Backend** — `SearchHit` carries `first_match_index: Option<usize>` (the 0-based index of the message containing the first query hit). `serde(default, skip_serializing_if = "Option::is_none")` so old hits without it still deserialize.
2. **`openItem(item, messageIndex?, query?)`** in App.tsx — sets `selected` AND a `pendingScroll = {sessionKey, index, nonce}` state. Nonce is `Date.now()`; same target clicked twice still re-triggers. A non-empty `query` additionally stages `pendingFind` (see "In-session find" below).
3. **Records renders**; once `detail.messages` loads, `MessageList` receives `scrollRequest` (only when `pendingScroll.sessionKey === selected`'s key).
4. **`MessageList`'s effect** fires a `requestAnimationFrame` → `virtualizer.scrollToIndex(idx, {align: "start"})` → `onScrolled()` callback.
5. **`clearPendingScroll = useCallback(() => setPendingScroll(null), [])`** in App.tsx nulls the state — required so the scroll doesn't fire again when the user selects another session and comes back.

The callback identity is stable (`useCallback` with empty deps) so the MessageList effect's dep array doesn't oscillate. SearchPage / CommandPalette pass `hit.first_match_index` through to `onOpenItem`; Favorites passes `source_message_index`.

## First-class projects, migration & deletion

### Project model (LOCKED)

A **project is a folder / entity each CLI keeps**, enumerated DIRECTLY and **independently of records** — a project shows because its entity exists, not because a record groups under it. `scan_sessions` returns `ScanResult { projects: Vec<Project>, records: Vec<AppSession> }`:

- `Project { source, project }` — `project` is the cwd string records also carry (the join key). There is **no `id`** and there are **no empty-project placeholders** anymore — the old `id == ""` placeholder approach (records masquerading as projects) was removed from BOTH backend and frontend.
- **`projects`** = `scan_project_folders()` + `opencode_empty_projects()` + `add_record_projects()`:
  - `scan_project_folders()` enumerates real folders — Claude: every `~/.claude/projects/<slug>` dir (cwd via `claude_cwd_from_project_dir` reading a sibling session, else lossy `decode_claude_project_slug`; slug must contain `-`); Gemini: every `~/.gemini/tmp/<id>/` with a `.project_root` marker (excludes `bin` etc.).
  - `opencode_empty_projects()` enumerates OpenCode's `project` table for rows with **no live top-level session** (OpenCode keeps projects independently of sessions; deleting/archiving a session doesn't drop the row) → a project keyed by `worktree`. (OpenCode projects WITH sessions come from `add_record_projects` by the session's `directory`; the two don't overlap, since "empty" means session-less.)
  - `add_record_projects()` fills in CLIs with **no folder entity** — Codex (sessions in one sqlite keyed by `cwd`) and OpenCode-with-sessions — by taking each session record's `(source, cwd)`.
- **`records`** = sessions + memory + skills (the contents inside projects), scanned separately.
- Consequence: a folder with sessions, with only auto-memory, or empty all show as a project; **deleting a record never removes its project** (the project stays until its folder is deleted).

### Memory terminology (do NOT conflate — safety-critical)

- **Auto-memory** — `~/.claude/projects/<slug>/memory/**.md` (Gemini: `tmp/<id>/memory/`). It lives **INSIDE the slug/hash folder**, so it's deleted when the project folder is deleted.
- **The project's own files** — `<cwd>/CLAUDE.md`, `AGENTS.md`, `<cwd>/.claude/...`. They live in the **USER's working directory, OUTSIDE the slug folder** → the backend **NEVER deletes them** (Termory only ever writes/deletes under `~/.claude/projects` & `~/.gemini/tmp`).

### Delete (Claude + Gemini; Codex/OpenCode have no delete yet)

Right-click actions in Records. The frontend **never sends a raw filesystem path** for delete/migrate — it sends `(project, rel)` and the backend builds the path under a bounded root.

- **Single record** (session / memory): `rel` = the file's path within its project dir (`recordRel(path)`). Backend joins it under `sanitize_claude_path(project)` (Claude) / the `.project_root`-matched tmp dir (Gemini), guarded by `is_safe_rel(rel)` (every component `Normal`; rejects `..`/absolute). Claude session delete also removes the companion `<id>/` dir.
- **Project**: `delete_claude_project(project)` → `remove_dir_all(~/.claude/projects/<sanitize(project)>)` (sessions + companion dirs + **auto-memory**, all inside the folder). `delete_gemini_project` removes the `tmp/<id>/` dir(s) whose `.project_root` matches. **Neither touches the cwd.**
- **Display = "no project → no data":** delete-project drops EVERYTHING shown under that project — sessions + auto-memory + the cwd's own `CLAUDE.md`/`AGENTS.md`/skills — from the UI via `projectDataMatch(source, cwd)` (`r.project === cwd && (r.source === source || ((memory||skill) && memoryToolsOf(r).includes(source)))`). The cwd's own files **survive on disk**; they just stop showing (the next scan won't return them once the project's sessions are gone).

### Migrate (Claude + Codex + Gemini + OpenCode + Grok)

`(project, rel, new_path, delete_old=true)` — MOVE mode. `migrate_claude_project` copies the whole slug subtree (sessions + companion dirs + `memory/`, skipping the regenerable `sessions-index.json` + `.DS_Store`) to the new path's slug, **rewrites only the top-level `cwd`** of each JSONL line (history content referencing the old path is left intact on purpose), then removes the old dir. `resolve_new_claude_dir` = slug of `fs::canonicalize(new_path)` **minus the Windows `\\?\` prefix**. Frontend remaps the moved records via `projectRecordMatch` (records under the slug folder). **mtime is preserved** on every migrated file (`preserve_mtime` after each `fs::write` / `fs::copy` in `copy_tree_rewrite_cwd` + the single session/memory writers) — `fs::write`/`fs::copy` reset it, but Claude's `/resume` list and Termory's mtime fallback order by it, so a naive copy would make every moved session read "just now" (same reason the Codex rollout rewrite restores mtime).

**Codex migrate** (`migrate_codex_session(id, new_path)` / `migrate_codex_project(project, new_path)`, IPC in lib.rs; returns `CodexMigrationResult { sessions, new_project }`). Codex has **no project folder** — a "project" is just `threads.cwd`, and the rollout JSONL files live under `~/.codex/sessions/` regardless of cwd — so migrating is a **pure metadata rewrite, no file relocation** (unlike Claude). The `threads` table is only a CACHE (Codex rebuilds `cwd` from the rollout's first-line `session_meta.payload.cwd` on backfill/resume reconcile — same story as `codex_follow.rs`'s model_provider), so `migrate_codex_threads_in` **rewrites each rollout file's `payload.cwd` FIRST** (`rewrite_rollout_cwd` — authoritative, atomic temp+rename, original mtime restored since the resume picker orders by file mtime), **then `UPDATE threads.cwd`** for the rewritten rows (file-first so a crash self-heals to the new cwd via backfill). Project migrate matches `where cwd = ?` (includes archived — whole-project move, consistent with `delete_codex_project`). `new_path` is canonicalized via `codex_canonical_cwd` (strips `\\?\`, falls back to the trimmed input when the dir doesn't exist yet). **Lower value than Claude migrate** — `codex resume <id>` already works across a rename (global DB keyed by id), so this is a regrouping convenience, not a "history lost" fix. Frontend `runCodexMigration` (migrate.ts) adapts the result to the shared `MigrateResult` shape with empty `old_dir`/`new_dir` (the record's path stays put; only `project` is re-pointed), and remaps via a direct `(source==="Codex" && project===old)` match — NOT `projectRecordMatch` (Codex rollout files share one `~/.codex/sessions` dir, so a folder match would hit unrelated sessions). Codex-specific i18n: `menu.migrateConfirmCodex` / `menu.migrateSuccessCodex`.

**Gemini migrate** (`migrate_gemini_project(project, new_path)`, IPC in lib.rs; returns `GeminiMigrationResult { sessions, new_project }`; **project-level only** — Gemini sessions are project-scoped (share one tmp slug dir), so there's no per-session/memory migrate). Gemini identifies a project by a slug in `~/.gemini/projects.json` **backed by `.project_root` ownership markers** under BOTH base dirs (`~/.gemini/tmp/<slug>/` and `~/.gemini/history/<slug>/`) holding the project's absolute path. `getShortId()` **SELF-HEALS the registry from those markers** — `findExistingSlugForPath` adopts a slug whose marker names the launch cwd, then rewrites projects.json + re-ensures markers (verified: gemini-cli `projectRegistry.ts:216-303` + `storage.ts` `initialize()`). So migrating is a **pure MARKER rewrite** — NO file move (the slug dir stays put, its whole history follows) and **NO projects.json write** (avoids gemini's `proper-lockfile` race; gemini reconciles the registry on its next run, and the stale old-path entry auto-removes when the old path is next opened — same "never write the CLI's live registry" stance as Claude's `~/.claude.json`). `migrate_gemini_project_in(tmp, history, project, new_path)` finds the slug dir(s) via `gemini_project_dirs` (`.project_root == project`), refuses when the destination already owns a Gemini dir (else two slugs collide → gemini's `ensureOwnershipMarkers` throws EEXIST), then `write_project_root_marker`s each tmp + sibling history marker to the destination (NO trailing newline, matching `ensureOwnershipMarkers`). **Marker value = `canonical_dest_dir`: CANONICALIZED (symlinks resolved)** — the SHARED helper grok also uses. gemini's `normalizePath` is `path.resolve` (no symlink resolution), BUT the QUERY it compares against is `process.cwd()`, which Node has ALREADY resolved — so the marker must be the resolved path or `verifySlugOwnership` fails on a symlinked destination. **This was caught by LIVE testing** (an earlier `NOT canonicalized` version made real gemini mint a fresh slug for `/private/tmp/x` instead of adopting the migrated one when the marker said `/tmp/x`). No mtime handling needed (session `.jsonl` files are untouched, so their resume-ordering mtimes are preserved). The result's `sessions` count comes from `count_gemini_chat_files`, which gates each `chats/session-*.{jsonl,json}` on the SAME `parse_gemini_session_file` (metadata_only) `hasResumableContent` rule the scanner uses — so the "Migrated N sessions" toast matches what Termory/gemini list, not the raw file count (startup-/command-/context-only shells are excluded). Frontend `runGeminiMigration` (migrate.ts) adapts to the shared `MigrateResult` (empty dirs; only `project` re-points) and remaps by `(source==="Gemini" && project===old)` like Codex (per-project memory/skills reconcile on the next scan). i18n: `menu.migrateConfirmGemini` / `menu.migrateSuccessGemini`. Tests: `sessions::tests::{migrate_gemini_project_in_rewrites_markers_and_counts_sessions, migrate_gemini_project_in_guards_source_dest_and_collision}`. **Live-verified end-to-end** (2026-07-18) against the real gemini binary on an isolated `$HOME`: after `migrate_gemini_project`, gemini launched in the destination cwd self-healed `projects.json` to the SAME migrated slug (both a canonical dest AND a symlinked `/tmp` dest — the latter is what surfaced the canonicalization fix).

**OpenCode migrate** (`migrate_opencode_session(id, new_path)` / `migrate_opencode_project(project, new_path)`, IPC in lib.rs; returns `OpencodeMigrationResult { sessions, new_project }`). Termory groups OpenCode records by `session.directory` (add_record_projects), so migrating is a **pure SQLite `UPDATE session SET directory = ?, path = NULL`** — session form `WHERE id = ?`, project form `WHERE directory = ?` (a directory belongs to exactly one project, so scoped). **`project_id` (the git-workspace `project` row) is deliberately LEFT INTACT**: the session stays attached to its project, so it never resurfaces as an empty project at the old cwd (`opencode_empty_projects` only lists session-less projects), and Termory never hand-writes OpenCode's internal `project`/worktree registry tables (verified schema: `core/src/{session,project}/sql.ts` — `project` keyed by `worktree`, a separate `(project_id, directory)` worktree-map table exists; touching those is unjustified for this feature). `path` (the nullable cwd-relative-to-worktree column) is set NULL so a stale relative path doesn't linger — OpenCode tolerates a null path (`listByProject` has an `isNull(path)` branch). Directory is stored absolute + forward-slashed on Windows (`database/path.ts` storagePath) — `opencode_directory_value` matches that: it runs the destination through the SHARED `canonical_dest_dir` (symlink-resolved — OpenCode also stores a resolved directory since it derives it from `process.cwd`, so canonicalizing keeps a migrated row in the SAME form as OpenCode's own rows and the grok/gemini migrates), then `\`→`/` on Windows. **LOW value** (like Codex): `opencode --session <id>` resumes by id regardless of cwd, so this is a Termory-display regrouping convenience, not a "history lost" fix (opencode's OWN per-worktree resume list won't move — `project_id` unchanged — which is the accepted tradeoff). Opens RW with the same `open_opencode_rw` (busy_timeout + `map_db_locked` "quit OpenCode"). Frontend `runOpencodeMigration` (session + project) adapts to the shared `MigrateResult` (empty dirs; only `project` re-points); wired in `ListItemMenu.tsx` (session) + the sidebar project row in `App.tsx` (by `(source,cwd)` like Codex/Gemini). **The session-row `onLocalMigrate` matches by `sessionKey`, NOT path** — OpenCode shares one db-file path across all sessions, so a path match would re-point the whole list (same reason as `onLocalDelete`). i18n: `menu.migrateConfirmOpencode` / `menu.migrateSuccessOpencode`. Tests: `sessions::tests::{migrate_opencode_session_in_repoints_directory_and_nulls_path, migrate_opencode_project_in_repoints_matching_directory_only}`. **Live-verified end-to-end** (2026-07-18) against the real opencode binary on a copy of the real db: after `migrate_opencode_session`, `opencode export <id>` read the session cleanly (DB uncorrupted) with `directory` = the new path and `path` = null. (The destination is canonicalized via the shared `canonical_dest_dir` for consistency with OpenCode's own resolved directories + the grok/gemini migrates.)

**Grok migrate** (`migrate_grok_session(id, new_path)` / `migrate_grok_project(project, new_path)`, IPC in lib.rs; returns `GrokMigrationResult { sessions, new_project, old_dir, new_dir }`). Grok is FILE-based: a session lives at `<grok-home>/sessions/<encode_cwd_dirname(info.cwd)>/<id>/` and grok's per-cwd resume scans EXACTLY `sessions/<encode_cwd_dirname(launch_cwd)>/` (jsonl/mod.rs:130), so — UNLIKE the metadata CLIs — the session dir must physically MOVE to the destination's encoded-cwd dir. `move_grok_session_dir` `fs::rename`s the `<id>/` dir into `<root>/<new-enc>/` then rewrites its `summary.json` info.cwd (mtime preserved — grok's cross-workspace recent list sorts by summary.json mtime; move-then-rewrite, and grok isn't running during a migrate). Session form resolves the dir via the scan path index (like `delete_grok_session`); project form scans for the encoded-cwd dir whose sessions record `info.cwd == project` (authoritative, never decodes the dir name — like `delete_grok_project`), moves all its `<id>/` dirs, then `remove_dir_all`s the emptied old dir (matching delete's "project moved away"). **`grok_encode_cwd_dirname` replicates grok's URL-encoding byte-for-byte** (paths.rs:112 — RFC-3986 unreserved `-._~` + alnum kept, else uppercase `%XX`); the long-path blake3 fallback (encoded > 255 bytes) is **refused** rather than pulling blake3 + slugify for a pathological >250-char cwd. **Destination cwd uses the shared `canonical_dest_dir` helper — CANONICALIZED (resolves symlinks)**: grok's cwd comes from the OS `current_dir` which resolves symlinks, so a session launched in `/tmp/x` scans the `/private/tmp/x` encoded dir. This was caught by LIVE testing against the real grok binary: a non-canonicalized `/tmp/x` destination made `grok -c` report "No session found"; canonicalizing to `/private/tmp/x` fixed it (test `canonical_dest_dir_canonicalizes_symlinks`). **`canonical_dest_dir` is shared with gemini + opencode** — all three CLIs derive/store their cwd from the OS `current_dir` (symlink-resolved), so all need the resolved form (gemini is the non-obvious case: its `path.resolve`-based comparison still needs a canonicalized input because its query is the already-resolved `process.cwd()`). Because paths CHANGE (file move, like Claude), the result carries `old_dir`/`new_dir` (the old/new encoded-cwd dirs) so the frontend `remappedPath` prefix-remaps moved record paths; `runGrokMigration` maps them into the shared `MigrateResult`. Search index (`session_search.sqlite` at the sessions root) needs no update — the session id (dir name) is unchanged, so its FTS doc stays valid. Wired in `ListItemMenu.tsx` (session) + the sidebar project row in `App.tsx` (by `(source,cwd)`, remap uses `old_dir`/`new_dir`). i18n: `menu.migrateConfirmGrok` / `menu.migrateSuccessGrok`. Tests: `sessions::tests::{grok_encode_cwd_dirname_matches_url_encoding, grok_dest_cwd_canonicalizes_symlinks, migrate_grok_project_in_moves_dirs_rewrites_cwd_and_removes_old, migrate_grok_session_moves_single_dir_via_path_index}`. **Live-verified end-to-end** (2026-07-18) against the real grok 0.2.103 binary on a copy of real session data: after `migrate_grok_project`, `grok -c` (continue-most-recent-for-cwd) in the destination dir resolved the migrated session (A/B: found at the new cwd, "No session found" at an unrelated cwd).

**MOVE semantics (LOCKED):** copy would leave the same session UUID in two slug dirs → `scan_claude_projects` dedups by UUID → the old project vanishes anyway + leaves hidden duplicates. So MOVE (remove old only **after** a complete copy). Backend keeps the `delete_old` flag (copy still tested); the frontend always sends `true`.

**`claude --resume` registration note (verified — not a Termory bug):** the moved files land in the right slug dir, but `claude --resume` (the command-line flag) only lists a project's sessions once that project is registered in `~/.claude.json` — and Claude registers a project when you OPEN it (run `claude` in the dir), NOT from the migrated files. So a project you've never opened in Claude won't list the moved sessions via the `--resume` flag until you run `claude` there once (afterwards `--resume` works too); **`/resume` inside a running Claude shows them regardless** (it reads the slug dir directly). Termory therefore: (1) **never writes `~/.claude.json`** — it's Claude's live config, rewritten by any running claude, so a concurrent write would clash; (2) on migrate, calls the **read-only** `claude_project_registered(new_path)` and, when unregistered, the confirm dialog adds a plain user-facing line (`menu.migrateConfirmUnregistered`) telling the user to run claude in the folder once. (Confirmed empirically: `claude --resume` of a never-opened project showed nothing; entering `claude` then `/resume` showed the migrated sessions.)

## UI conventions

### Internationalization (i18n)

The whole frontend UI is translated into **English / 简体中文 / 繁體中文** via a lightweight, type-safe in-house i18n (no `i18next` — the languages are a fixed bundled set, and Chinese has no plural rules, so the heavy machinery isn't warranted).

**Module: `src/i18n/`**

- `locales/en.ts` — the **source dictionary**. A flat `{ "dot.key": "text" }` object `as const`; its keys form the `MessageKey` union type.
- `locales/zh-Hans.ts` / `locales/zh-Hant.ts` — `Record<MessageKey, string>`, so **omitting any key the English dict defines is a compile error** (this is the completeness check — there's also a runtime test in `i18n.test.ts` asserting the three key sets are identical).
- `index.tsx` — `<I18nProvider>` + `useI18n()` / `useT()`, `{var}` interpolation, `resolveLocale()` (system locale → one of ours), and `LOCALES` (the picker list, each language shown in its own name).

**Wiring & behavior**

- `<I18nProvider>` wraps the app in `main.tsx` (outside `ThemeProvider`). It seeds the locale from `navigator.language` (`resolveLocale`), then overrides with the saved `language` config key on mount; `setLocale` persists back via `config.ts` and sets `<html lang>`. Switching re-renders all `useT()` consumers immediately.
- `useI18n()` falls back to a **default English context when no provider is mounted** (e.g. a unit test rendering a component in isolation) — so component tests don't need to wrap in `<I18nProvider>` and assert the English strings. `t()` itself falls back missing-translation → English → the raw key.

**Adding / changing UI text (the rule)**

1. Add the key to **`en.ts`** first (this defines the `MessageKey`), then add the SAME key to **both** `zh-Hans.ts` and `zh-Hant.ts` — the build breaks until all three have it. Keep keys grouped by area (`nav.*`, `search.*`, `stats.*`, `records.*`, `menu.*`, `providers.*`, `help.*`, `errors.*`, `toast.*`, `update.*`, `install.*`, `settings.*`, `command.*`, `favorites.*`, `footer.*`, `time.*`, `common.*`).
2. In the component: `const t = useT();` then `t("area.key")` / `t("area.key", { var })`. For a string passed to a child as a prop (e.g. `EmptyState title`, `Kpi label`, a const array of `{ labelKey }`), store the `MessageKey` and call `t()` at the render site. For module-level constants (preset/theme/shortcut tables) store a `labelKey: MessageKey`, not the literal.
- **Pure (non-React) helpers that produce UI copy take a translator param.** They can't call `useT()`, so the calling component passes its `t` in: `formatTimeAgo(ts, t)` / `formatRelativeDate(value, t)` (`src/lib/format.ts` — relative time like `time.justNow` / `time.minutesAgo` / `time.yesterday`) and `baseUrlHelp(app, npm, t)` / `apiKeyHelp(app, t)` / `overrideHelpFor(app, t)` (`src/lib/provider-utils.ts` — the editor's per-CLI help text). The format helpers keep `t` **optional** and fall back to English when omitted, so their pure-unit tests stay unchanged; the provider-utils helpers require it. The param is typed `Translate = (key: MessageKey, params?) => string` (provider-utils imports `MessageKey` from `@/i18n` — no cycle, since i18n imports `config`, not these).
- **Locale-aware date & number formatting follows the APP language, not the OS locale.** `src/lib/format.ts` keeps a module-level `currentLocale`; the `<I18nProvider>` calls `setFormatLocale(locale)` **in its render body** (not an effect — so it's set BEFORE children format in the same pass; the provider renders above all consumers). `Intl.DateTimeFormat` is rebuilt only on change (construction is expensive). Consumers: the cached date formatters (`formatDate` / `formatRelativeDate`) use it directly; ad-hoc `toLocale*` sites outside the module (FreshnessFooter tooltip, stats `formatDateLong`) read it via `getFormatLocale()`. `formatCompact` also branches on it — Chinese groups large numbers by **万 (10⁴) / 亿 (10⁸)** (`21.5B → 215亿`, `1.2M → 120万`), English keeps **K/M/B**. Without a provider (isolated unit tests) the locale is `undefined` = OS default, so existing tests are unaffected. Covered by `format.test.ts`.
- **English plurals** use two keys (`*_one` / `*_other`) selected by the caller (`t(n === 1 ? "x_one" : "x_other", { n })`); Chinese just maps both to one form.
- Brand / product names are **not** translated — they read identically in the zh dicts: CLI labels via `CLI_APP_LABEL`, `BrandIcon source`, **`AI Gateway` / `AI Gateways`** (the gateway product name — user decision), **`Base URL`**, **`AI SDK`**, **`Tokens`**, plus literals like `config.json`, `chmod 0600`, `sk-…`, and example URLs. `BrandIcon source` must stay a source literal, so translate the *display* text separately from the icon's `source` prop (see the Stats source-filter pills / sidebar "All", `MemoryCard`). (The "zh value == en value" set is the audit list for this — every entry must be a deliberate keep-English.)
- The gateway editor's add/edit dialog reuses **`providers.addProvider` / `providers.editProvider`** ("Add/Edit provider") — shared with the standalone provider editor, by user decision; the per-gateway-card edit icon keeps its own `providers.editGateway` tooltip.
- Toasts and `ask()` confirm dialogs are translated too; the only deliberate English left is `toast.error(String(err))` — a raw pass-through of a backend error with no template.
- The Rust backend's user-facing strings are mostly technical error pass-throughs surfaced via those `String(err)` toasts, so the backend is not part of the i18n system.

**Audit**: `i18n.test.ts` asserts the three key sets are identical. For dead keys (defined-but-unused) and placeholder-parity (the `{var}` set must match across all three locales or interpolation renders the literal `{var}`), there's no automated test — re-run an ad-hoc scan when in doubt (the last sweep found 0 mismatches; `providers.unmanaged` was the one dead key, since removed).

### Never hand-edit `src/components/ui/*` (LOCKED)

The files under `src/components/ui/` are stock shadcn/ui components — keep them unmodified. Do **not** hand-edit them to add styling or behavior.

Two documented baseline notes (2026-07-17): `command.tsx` is the untouched `npx shadcn@latest add command` output (an older hand-added `commandProps` passthrough was removed; CommandPalette composes `Dialog`+`Command` at the usage site to place `shouldFilter`). `dialog.tsx` carries ONE deliberate committed deviation — the overlay is `bg-white/20 dark:bg-black/30 backdrop-blur-xs` instead of stock `bg-black/50` (commit `5b02e89`, app-wide design decision; user-confirmed keep) — so a blanket CLI `--overwrite` of dialog WILL clobber it; restore the overlay line if a CLI update touches dialog.tsx.

- Need a new primitive (e.g. Collapsible, Accordion)? Add it with the shadcn CLI: `npx shadcn@latest add <name>`. It writes the stock component + pulls any radix dep. Don't hand-write the file.
- All customization (layout, spacing, animation, state) goes at the **usage site** via `className` / props on the consuming component, never inside `ui/*`. Example: the Custom config overrides collapsible in `ProviderEditor.tsx` applies its `grid`, `animate-collapsible-*`, focus-ring `-mx`/`px`, and trigger classes at the call site — `ui/collapsible.tsx` stays the untouched CLI output.
- Animation keyframes come from the already-imported `tw-animate-css` (`globals.css`), referenced via utility classes (`animate-collapsible-down/up`, `animate-in`, …) at the usage site — don't add `@keyframes` to component files.
- Verify before committing: `git diff --stat src/components/ui/` should be empty (new shadcn additions show as untracked files, which is fine).
- **Use the shadcn `Button` for standard action buttons** (`variant` = default / secondary / ghost / destructive; `size` = sm / icon-sm / …) instead of a hand-styled `<button className="…">`. Icon-only actions use `size="icon-sm"` (size-8); a destructive ghost icon (no shadcn variant for it) is `variant="ghost"` + `className="text-destructive hover:bg-destructive/10"`. A raw `<button>` is correct ONLY for things that aren't standard buttons: clickable list **rows/cards**, the activity **rail**, segmented **toggles/tabs**, filter **pills/chips**, and **inline-in-input icons** (e.g. the API-key eye toggle, `absolute`-positioned inside an `<Input>`) — shadcn Button's chrome would break those. (Converted ProviderCard / GatewaysPage / InstallGuide action buttons to `Button` in 2026-06; the rows/toggles/pills/inline-icons stay raw by design.)

### Tooltips (LOCKED)

Termory uses **shadcn `Tooltip`** (Radix-backed, mounted via `TooltipProvider` at root in `main.tsx`) — not raw HTML `title=` attributes. Native `title` was removed project-wide and replaced where the affordance is needed:

| Place | Trigger |
|---|---|
| Records detail reveal button (platform-aware label, shares `revealLabelKey` with the right-click menu) | shadcn `Tooltip` |
| `CopyMenu` trigger | shadcn `Tooltip` (suppressed while menu open via `open={menuOpen ? false : undefined}`) |
| `MessageList` star button | shadcn `Tooltip` (dynamic label: Add / Remove from favorites) |
| Per-message copy button (`MessageCopyButton` — every `MessageList` row + the Favorites detail message header; copies the message's raw markdown, 1.2s ✓ confirmation) | shadcn `Tooltip` (dynamic label: Copy / Copied) |
| Favorites detail "Open original session" + "Remove favorite" | shadcn `Tooltip` |
| Stats header compact-number chips (e.g. "1.2B tokens") | shadcn `Tooltip` showing `formatFullNumber(...)` |

Do NOT add `title="..."` to JSX. The reasons: (1) inconsistent styling vs the rest of the app, (2) no touch / long-press support, (3) browser-native tooltip can fight with focus-visible / aria-label, (4) shadcn version respects the project's color tokens.

Icon-only buttons still need an `aria-label` regardless of whether they have a Tooltip — screen-reader users don't trigger hover.

When a button opens a popover or dropdown that anchors on the SAME element (CopyMenu's case), suppress the Tooltip while the popover is open: pass `open={isOpen ? false : undefined}` to `<Tooltip>` so the two surfaces don't stack on the same anchor.

Tests that mount a component using `<Tooltip>` standalone (without the app's root `TooltipProvider`) must wrap their `render(...)` in a `TooltipProvider`. Pattern:

```tsx
function render(ui: React.ReactElement, options?: RenderOptions) {
  return rtlRender(<TooltipProvider>{ui}</TooltipProvider>, options);
}
```

  **Tool toggles (Settings → Tools; UI label "工具/Tools" — providers-first naming per John, i18n keys stay `settings.sources.*`).** config.json `sources` = `Partial<Record<CliApp, boolean>>`, absent key = enabled — EXCEPT default-off tools (`DEFAULT_OFF_KEYS` in config.rs ⟷ `DEFAULT_OFF_SOURCES` in provider-utils.ts, a keep-in-sync mirror pair): **gemini is OFF by default** (Gemini CLI stopped serving individual accounts 2026-06-18 — HTTP 410; enterprise Code Assist still works and the repo is still updated, Google steers individuals to Antigravity CLI) and needs an explicit `true` to show. The frontend gate is ALWAYS `isSourceEnabled()` in provider-utils — never inline truthiness. **Drag order:** the Settings → Tools rows are drag-sortable via **@dnd-kit/sortable** (`SortableSourceRow` in SettingsPage: PointerSensor with a 4px activation distance, `closestCenter` + `verticalListSortingStrategy`, grip-button-only listeners so the Switch stays clickable). Two hand-rolled iterations were REJECTED before landing here — HTML5 drag (WKWebView's native `dragDropEnabled` interception swallows the events, and drop-on-target can't insert after the last row) and raw pointermove reordering (midpoint oscillation, no cursor-following ghost). Don't re-attempt hand-rolled drag; the order persists as config `source_order` (CliApp[], same `source` family as the `sources` toggle key — the drag order is frontend-only, never read backend-side), is resolved by `orderSources()` (saved-first, unknown ids dropped, new tools appended — provider-utils + test), and drives Settings rows, Providers tabs, the Records sidebar pills, and Stats pills (all via App.tsx's `orderedCliApps`). The tray keeps `CliApp::all()` order (deliberate — not worth a snapshot field yet). Every tool is a full `CliApp` (grok included — it has provider switching), so ALL surfaces iterate `CLI_APPS`/`CLI_APP_LABEL`/`CLI_APP_SOURCE_BADGE` directly; the interim `ToolKey`/`TOOL_*` alias layer was deleted. Record/pill surfaces share the `visibleSources(order, toggles, {recordsOnly})` selector (provider-utils — excludes claude-desktop, which keeps no records). ONE backend filter point: `sessions::apply_source_toggles` post-pass at the end of `scan_sessions` (sessions/projects of a disabled source drop — source name lowercased == cli key, test-pinned convention; Memory/Skill records trim disabled tags from `preview` and drop when none remain), so Records / Search / Stats / the tray recent list all follow automatically. `refresh_session_path_index` runs BEFORE the filter so `load_session` by (source,id) still works for a disabled source (Favorites snapshots stay readable and by-id loads don't break; the FavoritesPage "Open original" button still hides via `sourceMissing` while the source is off — Records couldn't display it anyway). `write_app_config` (lib.rs) is a PER-KEY merge — the frontend `setConfig` sends only the ONE changed `{key, value}`; the backend reads the live config.json, replaces just that key, and writes it back (every other key untouched). When `key == "sources"` and its value actually changed (`obj.get("sources") != incoming`) → rescan + emit `SOURCES_CHANGED_EVENT` with the fresh ScanResult + `tray::refresh_recent` + full `rebuild_menu`. This per-key merge replaced the old whole-object write (frontend `flushConfig` → `writeConfigKey`), which round-tripped the entire startup cache and so resurrected renamed/orphan keys — a key ever written used to live forever (e.g. the retired `default_pane`, and, after an emptied file, everything came back). The disabled set RIDES IN `InstallSnapshot.disabled` (probed on the caller's thread, participates in the staleness compare) so the tray's `build_menu` / `terminal_clis` do zero config I/O on the main thread; quota triggers (`trigger_quota_refresh` / `force_quota_refresh`) skip disabled CLIs. Frontend: App.tsx owns `sourceToggles` (usePersistentState `"sources"`), filters the Records sidebar pills, guards the selected source / Providers tab back to an enabled one (plus a render-time clamp `effectiveProvidersApp` so Radix Tabs never sees a triggerless value for a frame), and threads the map to SettingsPage (Switch rows — the LAST enabled tool's switch is disabled, so all-off is unreachable) / StatsPage (pills) / ProvidersPage (tabs + `bindableInstalled` = installed ∧ enabled → GatewaysPage `installed`, + `enabledApps` → `visibleApps` → GatewayEditor rows & gateway-card binding rows, hidden not dimmed). **GatewayEditor `handleSave` carries hidden apps' existing bindings over VERBATIM** — rebuilding them from drafts would silently drop a disabled tool's binding on any save (regression test: "save preserves a hidden tool's existing binding verbatim"). Tests: `sessions::tests::apply_source_toggles_filters_sessions_projects_and_tags`, provider-utils `isSourceEnabled`, StatsPage disabled-pill, GatewayEditor visibleApps ×2.

- ~~Watcher completion~~ — done. The filesystem watcher (`src-tauri/src/watcher.rs`) **statically** watches the CLI data dirs (`~/.codex`, `~/.claude`, `~/.gemini`, opencode, the CLI-binary dirs for install detection) and **dynamically + recursively** watches each project's cwd — the dynamic set is recomputed from every scan's `projects` list (`dynamic_paths_from_sessions` over `result.projects` → `reconfigure_dynamic`, `RecursiveMode::Recursive`). So per-project files (`<cwd>/CLAUDE.md`, `AGENTS.md`, `.claude/skills/`, …) auto-refresh on edit too, not just at launch. A debounce (`DEBOUNCE_WINDOW` = 600ms) folds the flurry of fs events (incl. `node_modules` / build noise under the recursive cwd watch) into a single re-scan that emits `termory:sources-changed`. Net: **no manual per-source / per-file refresh is needed** — everything Termory surfaces lives under a watched path. **CPU: the `termory:sources-changed` emit is gated on main-window visibility** (`app_handle.get_webview_window("main").is_visible()`) — while the window is hidden (close-to-tray, a menu-bar app's common state) the re-scan still runs (the tray's `refresh_recent` needs it) but the full `ScanResult` is NOT serialized + sent to a frontend nobody's looking at. The frontend re-scans on window **focus** (`App.tsx` `getCurrentWindow().onFocusChanged` → a **silent** `scan_all_sessions` + `applyScanResult`, NOT `refresh()` — focus fires on every activation, so don't toggle the global `loading` or the Stats refresh indicator flashes; mirrors the sources-changed handler), and the next emit once visible is the fallback, so data is fresh whenever the window is shown. (During active CLI use the dominant per-scan cost is re-parsing the one changed session JSONL — mtime-cached so only the active file re-parses — plus this emit; the visibility gate removes the emit half whenever the window's hidden.)
